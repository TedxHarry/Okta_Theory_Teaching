Day 5: Questions

Groups and application relationships

Q01. A shared need

Question: A company approves Salesforce, a business application, for Sales employees. It uses Okta to manage identities and assignments. Instead of assigning the application to each employee separately, it connects Salesforce to a managed Sales employee group. What shared need does the group help maintain?

Read the teaching explanation

Explanation:

A group is a collection of users managed together. It gives the company one relationship through which members can receive the shared application assignment.

Who belongs in the group still needs an accurate maintenance mechanism. The group's connection to Salesforce is another relationship to configure and verify.

The benefit is managing the common assignment without repeating the normal decision independently for each user. It does not replace eligibility checks or prove usable application access.

Q02. A name is only a label

Question: An administrator creates an Okta group named Sales-Employees for a planned Salesforce access process. No membership rule, members, or application connection is supplied. Does the name itself define who belongs and connect Salesforce?

Read the teaching explanation

Explanation:

No. The name is a label describing intent, not an instruction that configures membership or assignments.

The group could be empty, contain unexpected users, or have no application connected. Inspect and configure the actual relationships according to the approved requirement.

A useful name helps locate an object. It cannot establish what that object does or whether a person's application assignment was produced through it.

Q03. Two relationships

Question: Okta manages a group called Sales-Employees. Devi’s membership is recorded, and a separate configuration assigns the Salesforce application to that group. How do those two relationships differ, and why inspect both?

Read the teaching explanation

Explanation:

The first relationship says, 'Devi belongs to this group.' The second says, 'Salesforce is assigned to this group.' Together, they provide her group-based assignment path.

Check what happens if either part is missing. Devi could be a member of a group with no Salesforce assignment. Or Salesforce could be assigned to a group Devi is not in. In either situation, this path would be incomplete for her.

Inspect both relationships and the resulting assignment for the intended Salesforce integration. That confirms how the assignment reaches Devi; the account and sign-in inside Salesforce still need their own checks.

Q04. Membership without the application

Question: Devi is a verified member of an Okta group intended to provide Salesforce, but the group has no Salesforce application assignment. No other path is supplied. Does this membership alone establish the expected group-based application assignment?

Read the teaching explanation

Explanation:

No. The user-to-group relationship is present, but the group-to-Salesforce connection is missing.

Compare that gap with the approved requirement and inspect the intended application instance. A membership rule that already placed Devi correctly is not the demonstrated problem.

Other paths and target outcomes need their own evidence if relevant. This question establishes one absent connection rather than every possible access result.

Rule inputs and purpose

Q05. Explain the rule’s job

Question: A company’s Okta rule evaluates department Sales AND workerType Employee to manage a designated group. Salesforce is separately assigned to that group. Which relationship does the rule manage, and which does the application assignment manage?

Read the teaching explanation

Explanation:

The group rule manages membership for qualifying users. The application assignment connects that group to Salesforce.

The rule is not itself a command to create an account inside Salesforce. Its membership result supplies an assignment path only because the separate application connection exists.

Follow the responsibilities: profile inputs, rule processing and membership, assignment, then the supported target account and sign-in work. Each outcome requires evidence rather than being assumed from the preceding step.

Q06. Workforce classification is a separate field

Question: A company defines workerType as a custom text attribute in its Okta user profiles, with Employee and Contractor as approved values. A user’s workerType is Employee. Does that mean the account is Active or identify its profile schema type?

Read the teaching explanation

Explanation:

Neither. WorkerType records the workforce classification defined by this company. Account status describes a different condition, and profile schema type concerns a different definition.

An Active user can be a Contractor. A stored Employee value does not independently establish that the account is enabled.

Read each field according to its purpose. Confusing classification with status could change who qualifies for a rule or hide a processing condition that still needs checking.

Q07. Who supplies classification?

Question: Salesforce eligibility depends on approved workerType values in Okta. Employees receive their classification from Workday HR; contractor data follows sponsor-approved maintenance by an authorized administrator. Why should users not set workerType themselves merely to gain an assignment?

Read the teaching explanation

Explanation:

The field represents the approved business classification, not a user-selected access option. The supplied maintenance paths govern its accurate value.

If information is wrong, correct it through the legitimate source or process. Changing Contractor to Employee simply to qualify would misrepresent the person and undermine the access requirement.

Eligibility relies on governed data. A desired application outcome should not become a reason to invent the identity facts feeding the rule.

Q08. AND in ordinary language

Question: An Okta group rule tests department equals Sales AND workerType equals Employee. A Boolean result is true or false. What does a true result mean, and does it by itself prove stored membership or usable application access?

Read the teaching explanation

Explanation:

Both conditions must be true for the supplied profile. The result establishes qualification for that input, not the completion of every later relationship.

Rule state, exclusions, and processing matter to actual membership. Application assignment and target use have additional checks.

Explain the condition in ordinary language: Sales and Employee must both be present. Then compare the prediction with the observed membership and relevant downstream results.

Predict the qualifying population

Q09. Predict three people

Question: An active Okta rule uses Sales AND Employee. Devi is Sales/Employee, Priya Sales/Contractor, and Daniel Finance/Employee. All three accounts are Active, processing is complete, no exclusion applies, and no other membership mechanism exists. Who qualifies for this rule-managed group?

Read the teaching explanation

Explanation:

Only Devi meets both conditions. Priya meets Sales but not Employee. Daniel meets Employee but not Sales.

The supplied processing conditions let the example connect those inputs to the expected rule-managed membership. Sharing one detail is not enough when AND requires both.

Those results implement the employee-only Sales population. Application assignment and actual use remain separate outcomes unless their evidence is also supplied.

Q10. Change AND to OR

Question: The approved population is Sales employees only. Devi’s profile is Sales/Employee, Priya’s Sales/Contractor, and Daniel’s Finance/Employee. If a proposed condition changes Sales AND Employee to Sales OR Employee, who qualifies and how does the requirement change?

Read the teaching explanation

Explanation:

All three qualify under OR. Devi meets both conditions, Priya meets Sales, and Daniel meets Employee. OR asks for at least one true condition; it does not exclude someone who meets both.

Compare that with the approved requirement: Sales employees only. Priya is a contractor, and Daniel works in Finance. Including them would broaden this rule beyond that requirement.

So changing AND to OR is a different access decision, not just a different way to write the same decision. Work out the affected people before applying it rather than test only whether Devi now appears.

Q11. Two meanings of Active

Question: In Okta, Devi’s user account is Active and a group rule is also active. The rule’s inputs, exclusions, processing result, and actual membership have not been inspected. How do those two uses of active differ, and is membership proven?

Read the teaching explanation

Explanation:

Active user describes account state. Active rule means the rule is enabled to operate. Neither alone establishes membership for Devi.

Read the relevant inputs, any exclusion, and processing and membership evidence. Account state is also a meaningful condition for rule behavior, not a synonym for qualification.

Keep the two facts separate. The same word appears in their labels while describing different objects and leaving the intended relationship unverified.

Q12. Unknown does not mean Employee

Question: A company’s normal Salesforce group requires Sales AND Employee. A user’s central Okta department is Sales, but workerType (the workforce classification) is missing. Can “not known to be Contractor” be treated as confirmed Employee?

Read the teaching explanation

Explanation:

No. Missing classification does not establish Employee. The user has not been shown to meet both required conditions.

Investigate the legitimate source, mapping, or approved maintenance process for the field. Do not supply the classification that would make access convenient.

Accurate data supports the approved population. An unknown input needs resolution, not a broader rule or an invented fact about the person.

Read the correct profile

Q13. Which profile is read?

Question: Workday HR supplies employee data to Okta. A configured attribute-based group rule reads the department and workerType fields in the central Okta user profile. Does the rule inspect Workday directly whenever support reads its condition?

Read the teaching explanation

Explanation:

No. The supplied rule evaluates the central Okta attributes. External information must first reach those fields through the applicable process.

Workday can be correct while the current input in Okta differs. Compare the approved source and actual rule input before changing the condition.

That can reveal a data-arrival discrepancy rather than a logic defect. The source you expect and the value the rule actually receives are different evidence questions.

Q14. Correct rule, stale input

Question: Devi’s approved Workday HR department is Sales, but her central Okta profile says Finance/Employee. The configured group condition correctly tests Sales AND Employee against that Okta input. Can its false result be logically correct while the business outcome is unwanted?

Read the teaching explanation

Explanation:

Yes. The rule is being given Finance/Employee. Employee is true, but Sales is false, so the AND condition is false. The rule can make that calculation correctly even though Devi's real approved department is Sales.

The disagreement is between the source value and the field the rule actually reads. Follow how Sales should reach her central Okta profile: check the linked records, incoming mapping and relevant import or update results.

Those checks can explain the discrepancy. Broadening the access rule would not repair the inaccurate input and could include other Finance users. Preserve the approved condition while investigating the demonstrated data gap.

Q15. Do not broaden around stale data

Question: The approved normal group is Sales AND Employee. Devi is legitimately Sales in Workday HR but stale as Finance in Okta, which the rule reads. No change allowing Finance users is approved. Why not add Finance to the group condition to include Devi?

Read the teaching explanation

Explanation:

It would change the qualifying population and could include other Finance employees. That exceeds correcting Devi's stale input.

Investigate why the approved Sales value is not represented in the central profile and preserve the employee-only Sales requirement.

A workaround can remove one symptom while creating unrelated assignments. Choose the correction at the demonstrated data discrepancy instead of changing the business access decision to accommodate it.

Q16. A target value is another layer

Question: A group rule reads Devi’s central department in Okta. Salesforce, a separate business application, displays Sales, but the central field has not been inspected. Does the application display establish the rule’s actual input?

Read the teaching explanation

Explanation:

No. The display concerns Salesforce's representation, not the central Okta field evaluated by the rule.

An app user profile is another layer: application-specific information prepared in Okta, distinct from the central profile and target account. Name the exact object and field being checked.

A correct-looking downstream value cannot certify an uninspected upstream input. Read the rule's actual source before explaining its result.

Condition, rule state, and membership

Q17. Saved is not activated

Question: An administrator saves a valid Okta group condition, department Sales AND workerType Employee, targeting a designated group. Activation and processing evidence are absent. Is a saved rule enough to report that it has managed membership?

Read the teaching explanation

Explanation:

No. A saved rule can remain inactive. The condition describes who should qualify, not whether the mechanism operated.

Check the rule state, target group, applicable exclusions, relevant account context, and actual processing and membership results.

The expression can be correct while the intended automatic path has not acted. Saving configuration and verifying its outcome are different observations.

Q18. A demonstrated inactive-rule gap

Question: Devi is Sales/Employee with an Active Okta account. The approved rule tests Sales AND Employee, targets the intended group, and has never been activated. Devi is absent and no other membership mechanism exists. Salesforce is assigned to the group. What gap is demonstrated?

Read the teaching explanation

Explanation:

The intended automatic membership mechanism is inactive. The condition matches and the application connection exists, but this rule has never operated.

The supported proposal is to activate the approved rule after reviewing its population and exclusions. Then verify membership and the resulting application assignment, followed by required target outcomes.

Changing correct HR data would address the wrong boundary. The configuration gap explains the demonstrated missing normal path without supplying a completed correction.

Q19. Review before activation

Question: A company proposes activating an approved but inactive Okta rule for all Sales employees. Devi’s missing membership led to the investigation, but the rule can affect other users. What should be reviewed before activation, and why?

Read the teaching explanation

Explanation:

Review the actual condition, designated group, affected population, and exclusions against the approved requirement. The shared rule is not private to Devi's account.

Activation is a configuration change with wider consequences. A single matching profile does not establish that every included user is intended.

After the appropriate change, compare actual membership and assignments with the predicted population. The investigation's initiating ticket and the change's scope can differ.

Q20. Matching but excluded

Question: Devi’s Active Okta profile is Sales/Employee. A rule requiring Sales AND Employee has an explicit exclusion for her, preventing this rule from adding her. The exclusion’s business justification is unknown. Does matching input prove the rule will include her?

Read the teaching explanation

Explanation:

No. Devi's profile meets the condition, but the rule also has an explicit exclusion for her. That exclusion prevents this rule from adding her; the two findings are not contradictory.

Before removing the exclusion, ask why it exists and whether that exception remains approved. Knowing how it affects membership does not tell us whether it should be changed.

Keep the scope of the finding. It explains why this rule does not add Devi. It does not tell us whether another group or a direct assignment gives her the application by a separate path.

Q21. Enabled but absent

Question: Devi’s central Okta profile is Sales/Employee, which matches an enabled Sales AND Employee rule. She is absent from the expected group. Her account-state context, applicable exclusions, and processing result are not supplied. Is a specific cause established?

Read the teaching explanation

Explanation:

The cause remains unresolved. Matching inputs and an enabled rule do not establish completed membership for this person.

Inspect the intended target group, account state, exclusions, and processing evidence. Those facts can distinguish why the expected relationship is absent.

Report the observed gap and next checks rather than declare a failed rule or deliberate exception without evidence. The missing result is clear even before its explanation is known.

Q22. A preview is not membership

Question: Devi’s Sales/Employee input produces true in a preview of an Okta group rule. A preview evaluates the condition, but stored membership and relevant processing have not been checked. What evidence is still required before reporting she belongs to the group?

Read the teaching explanation

Explanation:

Actual membership in the intended group is still needed. The preview establishes qualification for the selected input, not the stored relationship.

Rule state, exclusions, and processing can matter between that calculation and the result. Check them when membership is absent.

This is a useful distinction wherever systems calculate a proposed outcome: the calculation and the completed action are separate evidence. Keep the successful preview while requesting the actual membership result.

Q23. Manual removal as a test

Question: An Okta group rule manages a user’s membership. An administrator proposes manually removing that user and waiting for the rule to add them again. What effect makes removal an unreliable neutral test?

Read the teaching explanation

Explanation:

When you manually remove a rule-managed user from a group, Okta automatically adds that person to the rule's exclusion list. You have changed a condition governing later membership, so waiting for the rule to add them again is no longer a neutral test.

Inspect the resulting exclusion and management mechanism instead of assuming the original processing context stayed unchanged.

A test needs understood effects and scope. Repeating removal or waiting for re-addition can miss the very exception introduced by the test action.

What a confirmed assignment proves

Q24. Read the successful follow-up

Question: Support verifies Devi was added by the intended Okta group rule and has Salesforce assigned through that group. No Salesforce account state, account-management result, sign-in, or permission evidence is supplied. Which outcomes are established?

Read the teaching explanation

Explanation:

The rule-managed membership and group-based application assignment are established. Those are real successes in the normal path.

The target account, accepted application sign-in, and required permissions remain unverified. An assignment can initiate configured work, but it is not the target's completion receipt.

Report the verified relationships and follow the missing outcomes separately. Do not minimize the progress or stretch it into a claim that the whole application is usable.

Q25. Expected absence

Question: The normal Salesforce group rule is Sales AND Employee. Priya is Sales/Contractor and Daniel Finance/Employee; an active rule processed both without exclusions, and neither is a member. The checked snapshot confirms no other Salesforce assignment paths. Is their absence a malfunction?

Read the teaching explanation

Explanation:

Their exclusion is expected because neither meets both conditions. Priya fails Employee; Daniel fails Sales.

The supplied absence of other assignment paths also supports their Salesforce-assignment absence in this snapshot. That wider conclusion depends on the explicit path check.

A correct requirement can intentionally produce different outcomes for people sharing one attribute. Do not broaden the condition merely to make every profile qualify.

Q26. Assignment and usable access

Question: Devi’s Salesforce assignment is confirmed in Okta, the company identity service. Her requirement is entering the intended application account and performing an approved business action. No target-use evidence is supplied. Which separate outcomes still need verification?

Read the teaching explanation

Explanation:

Check the intended target account and relevant preparation result, accepted application sign-in, and permission for the approved action.

An assignment is a relationship in Okta. It does not demonstrate those separate results inside Salesforce.

State where the evidence stops so the next owner can inspect the actual missing boundary rather than repeat already verified assignment checks. The business requirement gives each verification a specific purpose.

Individual paths and approval

Q27. Priya’s individual assignment

Question: The normal Okta group includes Sales employees only. Priya is a Sales contractor, correctly absent from that group, but Salesforce is individually assigned to her. No exception approval is supplied. Does the direct assignment prove the employee group rule wrongly included her?

Read the teaching explanation

Explanation:

No. Priya is outside the employee group, just as the rule requires. The individual assignment connects her to Salesforce without using that group.

There are now two questions to keep apart: 'Did the employee rule include her?' and 'Is her individual assignment approved?' The supplied facts answer the first with no and leave the second open.

Inspect the actual assignment source and obtain the exception's business justification. Do not change a correct employee-only rule or label Priya an employee merely to explain an assignment that arrived through another relationship.

Q28. Missing approval evidence

Question: Priya’s Salesforce assignment is recorded as individual in Okta. The company requires contractor exceptions to be approved, but this review supplies no approval record or finding that approval does not exist. Is the observed path proven authorized or unauthorized?

Read the teaching explanation

Explanation:

Neither authorization conclusion is established. An observed assignment and its approval are separate questions.

Request the applicable requirement, accountable approver, current decision, scope, owner, and removal or review condition. Missing evidence in this review is not confirmed lack of approval in reality.

Describe the open decision precisely. That gives the responsible owner a useful action without inventing a permitted exception or a demonstrated violation.

Q29. Assignment source versus profile source

Question: Priya’s profile is maintained in Okta through an approved process. Her Salesforce assignment source is listed as Individual. Does this application-assignment label show a changed profile source, and what do the two meanings of source describe?

Read the teaching explanation

Explanation:

They describe different relationships. Profile source tells us which system controls Priya's profile data. Assignment source tells us which relationship gives her Salesforce.

Here her profile remains maintained in Okta under the approved process. Individual means Salesforce was assigned directly to her rather than through a group. It does not mean her data moved to a different profile owner.

When asking about a source, name what is being sourced: profile information or an application assignment. That small clarification keeps a data-maintenance decision from being confused with an access path.

Q30. Do not rewrite the person

Question: Priya is correctly classified as Contractor in Okta. Normal Salesforce eligibility requires Sales AND Employee, and contractor access may follow a separately approved exception. Why should support not change her workerType to Employee just to make her fit the normal rule?

Read the teaching explanation

Explanation:

It would make the profile misrepresent her workforce classification and undermine the approved eligibility condition.

Investigate the legitimate exception decision and path instead. The normal rule can correctly exclude contractors while a justified individual or separate group assignment exists.

Preserve accurate identity data. The desired access outcome should be implemented through its approved model, not by rewriting the person until a rule accepts them.

Moves and remaining paths

Q31. A future department move

Question: Devi moves from Sales to Finance under an approved change. The new Finance/Employee values reach her Active Okta profile, and an active Sales AND Employee rule processes them. In the stated group, that rule is the only membership mechanism and no exclusion issue applies. What membership is expected?

Read the teaching explanation

Explanation:

She no longer meets the Sales condition, so the simple rule-managed membership should be removed under the supplied conditions.

That is the predicted result; inspect actual membership and processing evidence to verify it. Then check application assignment paths separately.

A department change can end one qualifying relationship without establishing every target outcome. Keep the new input, rule result, remaining assignments, and application state as distinct observations.

Q32. Another group still assigns

Question: Devi’s membership in an Okta Sales group is confirmed removed. A different group still assigns Salesforce to her. No finding about removing that other path is supplied. Has the Sales-group removal ended every Okta Salesforce assignment path?

Read the teaching explanation

Explanation:

No. It ended that group's contribution while the other group's path remains.

Inspect all relevant assignment sources before claiming the final assignment has ended. Individual assignments can also be separate paths when present.

Ask which relationship stopped and which remain. A removed membership is useful evidence but cannot describe an independent relationship that still supplies the application.

Q33. Final assignment removed

Question: Support confirms the last Salesforce assignment path was removed from a user in Okta. No Salesforce account-state operation, target read, or existing-session test is supplied. Does the assignment result prove the target account is disabled and every session ended?

Read the teaching explanation

Explanation:

No. It verifies the relationship change in Okta, not those separate application outcomes.

Follow the supported account-management behavior and inspect the intended target record. If the requirement includes ending existing sessions, obtain the relevant application-side session result too.

The assignment can be removed while downstream work remains unknown or incomplete. Keep each required result open until the receiving system's evidence establishes it.

Q34. Order the move evidence

Question: An approved Sales-to-Finance move should end a user’s normal Sales group path. The rule reads the central Okta profile. Put these evidence checks in a useful sequence: target outcomes, updated profile, remaining assignment paths, rule processing and membership.

Read the teaching explanation

Explanation:

Check the updated profile, then rule processing and actual membership, then remaining assignments, and finally the relevant target outcomes.

That follows the dependency flow and helps locate whether the gap is data arrival, membership action, another surviving assignment, or downstream account/access behavior.

The sequence organizes investigation, not proof that the steps already occurred. Keep the identity and application instance consistent when joining their results.

Group ownership and Group Push

Q35. Who controls the group?

Question: Support can see several groups in Okta. Some may come from an external directory, some from authorized manual administration, and some from rules. A group’s management mechanism has not been inspected. Does visibility prove an Okta rule controls its membership?

Read the teaching explanation

Explanation:

No. Visibility identifies where the group can be inspected, not which process owns membership.

Determine the specific group's management mechanism before proposing an edit. A directory-sourced group follows a different path from a rule-managed or manually maintained group.

The name cannot establish the owner either. Actual configuration and relationship evidence explain how the current members were maintained.

Q36. Same name, different object

Question: Devi belongs to an Okta group that has Salesforce assigned. No configuration or target evidence establishes a group inside Salesforce. Does her Okta membership prove a same-named Salesforce group exists?

Read the teaching explanation

Explanation:

No. A group stored in Okta and a group stored in an application are separate objects.

The application assignment provides a relationship through which Okta members receive Salesforce. It does not automatically create the group inside Salesforce.

If target-group management is required, inspect supported configuration and actual destination evidence. Sharing a name cannot establish an object or link nobody has verified.

Q37. Assignment versus Group Push

Question: A company wants both group-based application assignment and target-group maintenance through Okta. Group Push is the capability for managing groups and memberships in supported applications. How do the two purposes differ, and can one result verify the other?

Read the teaching explanation

Explanation:

Ask what you want to manage. For group-based assignment, the question is 'Which users receive this application through an Okta group?' For Group Push, it is 'Which group and memberships should be maintained inside the target application?'

Those are separate relationships and separate results. A recorded application assignment does not show that a group was created in the target. Where Group Push is used, Okta requires separate groups for app assignment and Group Push; also check that the target integration supports the capability.

Verify the outcome you actually requested. If you need a target group, inspect its supported configuration and the target group itself. A successful assignment alone cannot answer that question.

Investigate and explain

Q38. A tile appears after a workaround

Question: Devi should receive an application through a normal rule-managed group, but that membership remains absent. An approved urgent individual assignment now makes her dashboard shortcut appear. No normal-path repair or target-use test is supplied. Is the membership problem resolved?

Read the teaching explanation

Explanation:

No. The direct path can provide an assignment without repairing the missing normal membership. The shortcut does not establish the target account, accepted sign-in, or permissions either.

Investigate the original gap and record the exception's owner and removal condition. Once the normal path is corrected, review whether the exception is still needed.

Keep workaround and repair as separate results. One visible improvement should not hide the unresolved relationship or verification.

Q39. Ask for the missing evidence

Question: Devi’s central Okta profile is Sales/Employee and the enabled rule tests Sales AND Employee. Expected membership is absent, but account-state context, exclusions, processing details, and other assignment paths are unknown. What focused evidence should support request before choosing a workaround?

Read the teaching explanation

Explanation:

Request the intended group's actual members, the rule's target and exclusions, Devi's account state, and relevant processing results. Inspect the intended application instance and assignment sources too.

Those facts distinguish possible explanations instead of assuming a failed rule or total assignment absence.

If an urgent exception is approved, track it separately with its end condition. Its existence does not supply the missing normal-path result or application verification.

Q40. Explain both access stories

Question: A company’s active Okta rule manages a group using Sales AND Employee. Devi is Sales/Employee and verified as a rule-managed member with Salesforce assigned through the group. Priya is Sales/Contractor, correctly excluded, and no other assignment path is supplied. Explain the different normal outcomes and what application-use evidence is still missing.

Read the teaching explanation

Explanation:

Devi meets both conditions, and the verified group relationship supplies her normal Salesforce assignment. Priya does not meet Employee, so she does not qualify for that normal path.

A separately approved exception could use another path if supplied; the rule alone does not describe every possible assignment. Here no such path is established for Priya.

The relationships explain normal assignments, not target-account readiness, completed sign-in, or business permissions. Those outcomes still need their own checks.
