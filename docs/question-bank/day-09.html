Day 9: Questions

OAuth, OIDC, and token purpose

Q01. Two related purposes

Question: Expense is a business application that needs to identify the person signing in and may separately need permission to call a protected API, an interface used by software. How do OAuth 2.0 and OpenID Connect (OIDC) address these related purposes?

Read the teaching explanation

Explanation:

Start with the two questions Expense needs to answer. 'Who is signing in?' concerns the person's identity. 'May this application call that protected service?' concerns resource access.

OAuth 2.0 provides the framework for obtaining authority to access protected resources. OIDC adds defined user-authentication information, including an ID token the client validates for sign-in. The resource service separately evaluates an access token presented for a request to it.

The two needs can occur in one application, but the tokens have different receivers and purposes. Identifying a person does not establish every business permission, and receiving an access token does not show an API call has succeeded.

Q02. Which receiver checks it?

Question: A business application uses OIDC for sign-in and receives an ID token and an access token. It can also call an intended protected resource service. Which receiver checks each artifact, and do readable user details make the access token a substitute for the ID token?

Read the teaching explanation

Explanation:

The OIDC client application validates the ID token for authentication information. The access token is presented to its intended resource server, often an API, which evaluates it under its own rules.

Readable user content does not change those purposes. Both tokens can arrive together while serving different receivers.

Name the artifact and receiving operation before selecting evidence. A resource-access value is not automatically the client's sign-in proof.

Q03. A token is not every outcome

Question: Devi’s Expense sign-in receives OIDC identity and access tokens from the company identity service. No account-management operation or expense-approval role is supplied. Does receiving those tokens automatically create an application account or grant approval rights?

Read the teaching explanation

Explanation:

No. The tokens have defined sign-in and resource-access purposes. Account preparation and business authorization are separate outcomes.

Expense still needs the intended account association and permissions for Devi's task. A token response is not a creation receipt or approval-role record.

Report the completed protocol stage accurately. If the request concerns usable access or a particular action, obtain the corresponding application evidence rather than extend the token result beyond its purpose.

Browser, backend, and client identity

Q04. Which client do you mean?

Question: Devi’s browser makes HTTP web requests, while Expense’s server-side backend acts as the OIDC application, exchanges a code, and validates identity information. Why can both be called a client in different contexts without referring to Devi’s user account?

Read the teaching explanation

Explanation:

Client names a participant's role in a particular exchange. The browser is an HTTP client; Expense is the OIDC client application in the sign-in protocol.

Its backend performs the code exchange and validation while the browser carries the redirects. The application registration is different from the person's account.

Name the exchange when using client. That keeps software responsibilities and user identity separate during investigation.

Q05. Why confidential?

Question: Expense is an OIDC web application with a backend running on its servers. The backend can protect a configured credential or key and performs the code exchange. Why is this design a confidential client, and which work belongs outside the browser?

Read the teaching explanation

Explanation:

Here, confidential describes Expense's ability to protect its client authentication material on its servers. It does not mean the client ID has to be hidden, and it does not describe Devi's user account.

The backend performs the code exchange and validates the returned identity information. Its configured credential or key stays protected there, outside the browser redirect. The browser carries messages between the services; it does not perform every backend operation.

Keep this architecture in view when choosing evidence. A code arriving through the browser tells you where the journey has reached. You still need the backend exchange and application results before reporting completed sign-in.

Q06. Client ID is not a secret password

Question: Expense’s OIDC registration has client ID nb-expense-web. Its backend separately authenticates at code exchange using its configured credential or key. What does the ID identify, and is the visible ID itself a password or proof that the exchange succeeded?

Read the teaching explanation

Explanation:

The ID names the application registration. It is not Devi's identity, a password, or an accepted client-authentication result.

The backend's configured authentication separately proves the client during exchange. Its confidential material should stay protected on the server side.

Identifying and authenticating the application are different facts. Inspect the actual exchange result rather than infer success from a familiar client identifier in the request.

Q07. Okta’s roles

Question: In a stated OIDC connection, Expense is the client application and Okta applies the relevant requirements and issues responses and tokens. What does Okta’s authorization-server and OpenID-Provider role contribute, and what must Expense still do?

Read the teaching explanation

Explanation:

As authorization server, Okta issues OAuth responses and tokens under the configured requirements. In OIDC it also acts as OpenID Provider supplying authentication information.

Expense still validates its returned ID token, associates the user with the intended local account, and establishes its application outcome.

These roles describe this connection. They do not make the provider's result evidence that every client-side validation or business permission succeeded.

Trace the code journey

Q08. Trace the intended journey

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. Describe the intended browser return, backend exchange, and application decision in order, without treating the design as proof of a completed attempt.

Read the teaching explanation

Explanation:

The browser carries code and state to Expense's registered callback. Expense checks the returned transaction, and its backend exchanges the code under the required client-authentication and PKCE checks.

The token response returns to the backend. Expense validates the ID token, selects the intended account, and establishes a session.

Those are intended stages, each needing actual result evidence. A route explains who acts next; it does not establish that every stage completed.

Q09. Three locations

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. How do the authorization endpoint, token endpoint, and callback describe different addresses and operations?

Read the teaching explanation

Explanation:

Picture who receives each message. The authorization endpoint belongs to Okta in this example and receives the authorization request. Expense's callback receives the browser's return with the code. Okta's token endpoint receives the backend's code exchange.

That gives you a route: browser to Okta, browser back to Expense, then Expense's backend directly to Okta. The callback is not the address where the backend redeems the code.

Each address has a different operation behind it. Seeing the browser reach Expense's callback cannot establish that the later exchange at Okta's token endpoint succeeded or that Expense validated the returned ID token.

Q10. The code is an intermediate artifact

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. The browser returns a code, but no exchange response, token validation, or session result is supplied. Why is code receipt an intermediate result rather than completed application sign-in?

Read the teaching explanation

Explanation:

An authorization code is a temporary, single-use value exchanged for tokens. It is not the ID token the client validates for authentication information.

The backend exchange still has requirements and a result. The returned identity information then needs validation and an intended account association.

Report the code return as progress. Do not call a session established until its relevant application evidence exists.

Q11. Not an MFA code or API credential

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. Is the returned authorization code something Devi types like an MFA code, or a value Expense should use directly to call a protected API?

Read the teaching explanation

Explanation:

Neither describes this architecture. The browser delivers the code to the callback, and the backend presents it to the token endpoint for exchange.

An MFA code is a different user authentication interaction. A resource call instead uses an appropriately issued access token under the receiver's rules.

The shared word code does not make the artifacts equivalent. Follow the actual purpose and recipient before interpreting what one result establishes.

Q12. Session, code, and token

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. After successful validation the application establishes a session for continued use. Is that session another name for the authorization code or ID token?

Read the teaching explanation

Explanation:

No. Follow what each one does. The authorization code lets Expense's backend request the token response. The ID token provides authentication information that Expense must validate. The application session lets the signed-in person continue interacting with Expense under its own session rules.

The session is an application result, not a new name for either earlier value. A returned code does not show it exists, and a readable ID token does not show validation or entry succeeded.

This distinction also matters after a change. An older working session can let someone continue using Expense without running the newly changed sign-in journey. A fresh attempt is needed to verify that path.

Q13. Must every prompt appear?

Question: An OIDC application starts an authorization request through the company identity service. The applicable policies and existing authentication context determine the interaction. No screen trace is supplied. Must every request show a new password prompt and consent screen?

Read the teaching explanation

Explanation:

No. The actual interaction depends on the requirements and existing context. A simplified flow does not guarantee the same screens every time.

Inspect the identified attempt's records rather than invent prompts. The core stages still need their own request, return, exchange, and validation results.

Visible interaction is useful evidence, but the protocol journey cannot be reconstructed solely from an assumed standard screen sequence.

Request fields and transaction checks

Q14. Read the selected parameters

Question: A fictional OIDC authorization request includes client_id nb-expense-web, response_type code, and redirect_uri https://expenses.example/callback. No request acceptance result is supplied. What purpose does each field describe, and what outcome remains unverified?

Read the teaching explanation

Explanation:

Client ID names the application's registration. Response type code asks for an authorization code. Redirect URI gives the requested browser return location.

They describe what the client asks for, not proof the server accepted it or issued a code. Compare the emitted values with the approved registration.

Configuration and the actual request can disagree. Reading these fields helps locate that comparison without turning the requested behavior into a completed result.

Q15. Scope and claim

Question: An OIDC request asks for scope openid profile. Returned information may contain named statements called claims, such as a subject identifier. How does the requested scope differ from the content actually returned, and is every imaginable profile field guaranteed?

Read the teaching explanation

Explanation:

A scope describes what the application requests. In this example, openid requests OIDC behavior and profile requests the supported profile-information category. A claim is a named statement actually returned, such as the subject identifier.

Asking for a category is different from seeing a particular value in the response. The profile request does not guarantee every imaginable profile field, or that every field appears in the ID token.

Inspect what was returned and whether it passed the required validation. Even a validated name or profile detail does not by itself establish a business role such as permission to approve expenses.

Q16. Profile is not an approval role

Question: Expense uses OIDC sign-in. Devi’s request includes the profile scope and the returned identity information contains her name. No application approval decision or role is supplied. Does that identity detail prove she can approve another person’s expenses?

Read the teaching explanation

Explanation:

No. The name concerns identity information, not a business permission. Authentication and application authorization answer different questions.

If approval is required, establish the authorized capability and actual role or action result inside Expense. A sign-in protocol can identify someone without granting every function.

Keep the claim's purpose narrow. Readable profile data does not become authority simply because the application receives it.

Q17. State’s return check

Question: Expense starts an OIDC browser sign-in and sends a fresh state value with its authorization request. The browser response returns a state value with the code. Where is state checked, and what relationship does the comparison establish?

Read the teaching explanation

Explanation:

Expense compares the returned state with the transaction it started. This helps connect the browser response to the expected request.

The field's mere presence does not establish a matching result. Inspect the actual comparison outcome for the attempt.

Passing this check also does not verify code redemption or ID token validity. It belongs to one boundary in the larger journey, with separate results needed afterward.

Q18. Nonce’s later check

Question: Expense’s OIDC request sends both state and nonce. State returns with the browser response; nonce is later compared within the returned ID token. How do their check locations differ, and can matching state replace nonce validation?

Read the teaching explanation

Explanation:

Expense checks state when the browser returns. It compares the returned value with the one kept for the transaction it started. That answers, 'Does this browser response belong to the attempt I began?'

Nonce is checked later, inside the returned ID token. Expense compares that value with the nonce sent in the authentication request. That answers a related question about the returned identity information, at a different point in the journey.

Because this request includes nonce, matching state does not remove the nonce check. A matching value at one stage cannot stand in for the other stage's result or the remaining token validation.

PKCE and the backend exchange

Q19. Verifier and challenge

Question: Expense uses Proof Key for Code Exchange (PKCE) during OIDC code flow. Its backend creates a secret code verifier and sends a derived challenge with the authorization request. What does it retain, and what is supplied and checked during redemption?

Read the teaching explanation

Explanation:

Expense keeps the secret verifier for this transaction. It sends the derived challenge with the earlier authorization request, so the authorization server can associate that challenge with the code it issues.

When the backend redeems the code, it supplies the retained verifier. The authorization server checks whether it matches the earlier challenge using the configured method. The code alone does not supply that required proof.

Think of the order: create and retain the verifier, send its derived challenge, then present the verifier during exchange. This transaction secret is different from the person's password. A returned code is still an intermediate step with an exchange result to establish.

Q20. A code without its verifier

Question: An OIDC code exchange requires PKCE: the client first registers a challenge derived from a secret verifier, then must present the matching verifier when redeeming the code. Someone obtains the code without that verifier. What required proof is missing?

Read the teaching explanation

Explanation:

The person lacks the matching verifier checked against the earlier challenge. Code possession alone does not supply that required redemption proof.

PKCE helps protect against code interception or injection. The server still needs to perform the check for the relevant code and transaction.

This is one exchange requirement, not a replacement for every other validation. Identify which proof is required at each stage and obtain its actual result.

Q21. What S256 names

Question: An OIDC request uses code_challenge_method S256 for PKCE, which checks code redemption against a transaction verifier. Does S256 identify the user or an application permission, and what calculation role does it name?

Read the teaching explanation

Explanation:

It names the challenge method. A SHA-256 one-way cryptographic calculation and URL-safe encoding derive the challenge from the verifier.

The authorization request sends that derived challenge; the backend retains the verifier for redemption. The label is not a user account or role.

You need not calculate it to investigate the flow. Recognize the expected fields and check the actual exchange evidence when a result is missing or rejected.

Q22. PKCE and client authentication

Question: Expense is a confidential OIDC client with a server-side backend that protects its credential or key. The supplied design requires both PKCE proof for code redemption and configured client authentication. Does using PKCE remove the client-authentication requirement?

Read the teaching explanation

Explanation:

No. The question's design requires both checks, and they prove different relationships. Client authentication asks the backend to prove which registered application it is using its configured credential or key. PKCE asks for the verifier associated with this particular code request.

A client credential identifies the application's authentication relationship. A verifier belongs to a transaction. Supplying one does not establish that the other requirement passed, and neither is the user's password check.

If the exchange fails, inspect its client-authentication and PKCE results before choosing a correction. Do not remove a stated requirement simply because the other check succeeded.

Q23. Locate three checks

Question: Expense starts OIDC requests with state, nonce, and a PKCE challenge. Its browser returns code and state; its backend exchanges the code with a verifier; an ID token is returned. Where are the three relationship checks performed?

Read the teaching explanation

Explanation:

Expense checks returned state at the browser response. The authorization server checks the PKCE verifier during code exchange. Expense compares nonce within the returned ID token.

They answer different transaction questions at different stages. Passing one does not establish the other two or remaining token validation.

Place the checks on the journey instead of treating them as interchangeable security words. The last completed stage helps identify which result to request next.

Three artifacts and their receivers

Q24. Code, ID token, access token

Question: In a server-side OIDC flow, a browser delivers an authorization code; the backend exchanges it for an ID token and access token. Match each artifact to code exchange, authentication-information validation by the client, or a protected-resource request.

Read the teaching explanation

Explanation:

The code is presented to the token endpoint to obtain the token response. The client validates the ID token for authentication information. The access token is presented to its intended resource server for resource access.

Each has a receiver and purpose. They are not interchangeable because they belong to one sign-in journey.

Name the artifact and operation before claiming a result. The appropriate receiver supplies the validation evidence for its boundary.

Q25. Token received versus API used

Question: Expense’s OIDC backend receives a token response containing an access token, which may be presented to an intended protected API. No API request or resource-server response is supplied. Has a successful resource call been established?

Read the teaching explanation

Explanation:

No. The response establishes receipt of the token, not that it was used or accepted by a resource service.

If a permitted call is part of the requirement, inspect its actual request and the intended receiver's result. The token needs to be suitable for that resource under its rules.

Receiving material for a possible later operation is not evidence the operation occurred. Keep the artifact and subsequent action distinct.

Q26. Bearer’s meaning

Question: A token response labels an access token Bearer. A bearer token may be presented to its intended resource service subject to validation. No resource request is supplied. What does the label mean, and does it establish successful use?

Read the teaching explanation

Explanation:

Possession is sufficient to present the token for use, subject to the receiver's validation. Treat a usable bearer value as sensitive.

The label does not establish receipt or acceptance by the resource service. That operation needs its own result.

Request relevant errors and identifiers without copying complete usable tokens into a ticket. The investigation needs evidence about the operation, not redistribution of its credential.

Q27. Not valid for every API

Question: Okta issues an access token for a configured client. Support wants to use it at another API whose intended audience, issuer agreement, scopes, and validation rules are unknown. Is issuance by the familiar identity service enough to establish that API will accept it?

Read the teaching explanation

Explanation:

No. The intended resource and validation contract determine where the token can be used. Issuer familiarity does not provide universal authorization.

Identify the actual receiving API and its requirements before interpreting the token's suitability. No successful call to the other service is supplied here.

Keep the issued artifact's purpose attached to its configuration. A token is not automatically valid everywhere a client wishes to send it.

Read and validate identity claims

Q28. Read iss, sub, and aud

Question: A fictional single-audience OIDC ID token has selected claims iss = https://identity.example, sub = subject-devi, and aud = expense-web. Claims are named statements in returned information. What do these three fields describe, and does reading them establish validity?

Read the teaching explanation

Explanation:

Iss names the issuer. Sub identifies the subject within that issuer. Aud names the intended audience, here the client registration expense-web.

They help compare the payload with expected settings. Reading them does not verify signature, validity, nonce, or the complete token.

Use content inspection for what the message says, and validation evidence for whether the client may rely on it. Correct-looking fields are not a complete acceptance result.

Q29. Issuer and subject together

Question: Expense associates a validated OIDC identity using the issuer and subject pair, iss and sub. An email-like attribute may also be returned. Why keep issuer context with sub instead of assuming email is an immutable identifier for everyone?

Read the teaching explanation

Explanation:

Read the pair as 'this subject, as identified by this issuer.' The issuer supplies the context in which the subject identifier has meaning. The same subject text from a different issuer does not automatically describe the same person.

Expense uses the validated issuer/subject pair to find the intended local account in this scenario. An email-like attribute can be useful information, but it is not automatically that association key or an identifier that never changes.

First validate the identity information, then inspect the configured account association. A familiar email address cannot substitute for either step.

Q30. Decoded JSON is not verification

Question: Support decodes an OIDC ID token represented as a JSON Web Token (JWT) and sees the expected audience. Signature verification, issuer, time validity, and the nonce sent for the request have not been checked. Is complete ID token validation established?

Read the teaching explanation

Explanation:

No. Decoding reveals claims; it does not establish authenticity or every acceptance condition.

Use the actual token and trusted provider information for the required cryptographic validation, then the other applicable checks. The expected audience is one useful comparison, not the whole result.

Keep reading and validating separate. A selected JSON view cannot supply omitted signature or transaction evidence.

Q31. JWT shape does not decide purpose

Question: A data string has the familiar format of a JSON Web Token (JWT). Its issuer, purpose, audience, signature, and receiving contract are unknown. Does that shape automatically make it an acceptable ID token or access token?

Read the teaching explanation

Explanation:

No. Format is not enough to establish purpose or trust. The issued artifact and the receiver's requirements determine how it may be used.

Check who issued it, its intended recipient and transaction, validity, and required cryptographic verification. Reading its content is not acceptance evidence.

A token-shaped value can be inspected without being suitable proof. Attach conclusions to actual validation rather than to a recognizable appearance.

Q32. A correct audience, wrong nonce

Question: Expense sends a nonce in its OIDC request and requires the returned ID token to match it. The token’s audience agrees with the client ID, but nonce differs from the original value. Can audience matching substitute for that transaction check?

Read the teaching explanation

Explanation:

No. Audience names the intended client. Nonce connects the returned identity information to the authentication request in this scenario.

Read the actual validation result and transaction context before choosing a correction. The audience success does not erase the separate nonce discrepancy.

The checks protect different relationships. Preserve a passed condition while investigating the one that disagrees with the supplied requirement.

Compare, review, and explain

Explanation:

The SAML receiver validates the assertion under its connection agreement. The OIDC backend first exchanges the code and then validates the ID token and transaction.

Both need the intended account association and actual application outcome. Their artifacts and checks are different, so the browser returns cannot be substituted for one another.

Neither design by itself proves account creation or every business permission. Follow the protocol actually supplied.

Q44. Explain Devi’s journey

Question: Expense is a business application using OIDC with Okta. Its server-side backend exchanges authorization codes and validates ID tokens; Devi’s browser carries redirects. First attempt: an obsolete unregistered callback is rejected before code issuance. New follow-up: the approved address, state, authenticated PKCE exchange, ID token checks, intended account, and entry all succeed. Permission results are not supplied. Explain both outcomes to Devi in friendly language.

Read the teaching explanation

Explanation:

You could say: 'Expense first asked Okta to send your browser back to an old return address that was not approved. Okta stopped that request before issuing a code, so the application could not continue the sign-in exchange for that attempt.'

Then describe the checked follow-up: 'The new attempt used the approved return address. Expense checked the browser return, completed its server-side exchange and validated your identity information. It then recognized your intended account and let you in.'

If Devi needs an approval action, add: 'We still need to check whether your account has permission for that action.' This explains the two observed outcomes without turning the later success into what happened during the first attempt or promising permissions that were not checked.
