Day 12: Questions

Business events and scoped states

Q01. Join, move, leave

Question: An identity team receives three approved events: Maya starts employment, Daniel changes responsibilities while remaining employed, and Jordan leaves. How do joiner, mover, and leaver describe the different access goals for these events?

Read the teaching explanation

Explanation:

A joiner starts work, a mover changes responsibilities, and a leaver departs. Together these are often called JML. Start with the approved business outcome rather than choosing the same account action for all three.

The joiner needs the access required to begin work. The mover may keep some access, gain another capability, and lose obsolete paths. The leaver needs access to end across the agreed scope. Each goal requires evidence from the affected systems.

Q02. Inactive where?

Question: A departure ticket includes only the note “Jordan is inactive.” His employment record, Okta identity, Projects application account, and application sessions may each have separate states. What must support clarify before treating this as access-removal evidence?

Read the teaching explanation

Explanation:

Ask 'Inactive in which system, on which record, and according to what check?' The note could refer to Jordan's employment, his Okta account, an application account or a session. Those do not describe the same outcome.

For example, 'the checked Okta identity is DEPROVISIONED' identifies an account and its observed status. It does not tell you whether Projects is inactive or Expense still accepts a session.

Request the actual observation behind the note, then compare it with the approved removal requirement. Different states can coexist while departure processing remains unfinished, so a precise finding helps identify what still needs attention.

Q03. The effective point

Question: HR records a future employee start today, while a departure event arrives before downstream applications finish removing access. How does an approved event’s effective point differ from its arrival time and the completion of target changes?

Read the teaching explanation

Explanation:

Keep three times in view. The effective point says when the approved access change should apply. Arrival says when the process received the event. Completion says when the required downstream change actually finished.

A future start entered today can support preparation without authorizing working access today. A departure event arriving on time can still be followed by an unfinished application removal.

Compare the observed results with the approved timing. Receiving the information is useful progress, but it cannot establish when every target achieved the required account or access state.

Q04. Data change versus lifecycle action

Question: A Workday employment field changes for a correctly associated employee. The company has configured lifecycle processing in Okta, but no account action or downstream result has been inspected. Does the changed field establish that the required lifecycle action occurred?

Read the teaching explanation

Explanation:

No. The field is profile data. The configured process must interpret the relevant event, act on the correct identity, and produce the intended account and access results.

Follow the source relationship, processing evidence, and resulting operations. A changed value is a meaningful observation, but it does not supply a missing action or a target outcome. The intended lifecycle change can remain pending even when the source information is correct.

Interpret Okta statuses and lifecycle actions

Q05. Active is a scoped state

Question: A read of Maya’s Okta user returns status ACTIVE. Her current employment approval, application accounts, actual sign-in, and business permissions have not been reviewed. What does this account status establish, and which conclusions need separate evidence?

Read the teaching explanation

Explanation:

ACTIVE establishes that the checked Okta account is enabled. It does not independently establish ongoing employment, successful application entry, or the permissions needed for Maya's work.

Authentication requirements may still apply, and each application has its own records and access conditions. Use the status as one finding, then follow the approved requirement to the missing checks. An enabled identity is useful context, rather than proof of every business outcome.

Q06. PROVISIONED does not mean Projects created

Question: An Okta user-list response shows API status PROVISIONED, whose Admin Console label is Pending user action. No create request or read of the person’s Projects application account is supplied. Does the Okta status verify that Projects was provisioned?

Read the teaching explanation

Explanation:

No. Start with the system that returned the status: this is an Okta user-list response. PROVISIONED means Pending user action in that account's activation context, not 'Projects has created this person's account.'

To establish the Projects outcome, inspect the relevant account-management operation, its response and the intended target record. None of those results is supplied by the Okta status here.

The familiar word can cause the confusion. Keep the status attached to its account, and describe application provisioning through that application's actual operation and result.

Q07. Staged is not a fixed route

Question: A newly created Okta identity is STAGED, meaning activation has not been initiated or administrative action remains. The organization has different creation and authentication arrangements for different users. Must every identity pass through all available statuses in one fixed sequence?

Read the teaching explanation

Explanation:

No. The status names describe distinct account conditions, not mandatory stations in a universal route. Creation, authentication arrangements, and configured lifecycle behavior affect which states occur.

Inspect the actual process and the approved start before deciding what should happen next. STAGED identifies this account's current condition, but it does not establish readiness for work. A memorized sequence cannot replace evidence of the intended activation and application outcomes.

Q08. Different problems, different states

Question: Three employed users have Okta statuses RECOVERY, PASSWORD_EXPIRED, and LOCKED_OUT. A fourth person has an approved effective HR departure. Why should support distinguish these conditions instead of treating each as the same lifecycle event?

Read the teaching explanation

Explanation:

RECOVERY concerns password recovery, PASSWORD_EXPIRED requires a password update, and LOCKED_OUT indicates a lockout condition. These describe account conditions rather than an employment decision.

The departure supplies a different business requirement: access must end across its agreed scope. Read the account state alongside the source relationship and approved event before choosing an action. Password recovery does not renew employment approval, and a lockout does not prove the person has left.

Q09. What suspension retains

Question: A company approves a temporary suspension of Maya’s Okta access. Support needs to understand what suspension retains before planning a later return. How do application assignments and group memberships behave, and what still requires target-specific evidence?

Read the teaching explanation

Explanation:

Suspension blocks Okta access while retaining application assignments and group memberships. Unsuspending that account is therefore a different decision from reconstructing access removed by deactivation.

Check the approved situation and the relevant target accounts and sessions where required. The known Okta action has a specific scope; it should not be reported as verified removal everywhere. Retaining relationships helps explain the later decision, but it does not settle every application's observed access.

Q10. Read deactivation’s result

Question: An approved departure triggers Okta deactivation, which removes app assignments, invokes applicable configured deprovisioning, and retains group memberships. The action is requested, but background completion and target results are unchecked. Can support report the departure complete?

Read the teaching explanation

Explanation:

Not yet. Requesting the action is different from verifying completion. Check the completed Okta result and the relevant account read, then follow each required downstream operation and access outcome.

Deactivation is also distinct from deleting the identity. Even a completed Okta deactivation does not supply every application's result. Keep the initiating action and its target effects separate so a requested operation does not become an unsupported claim of complete departure.

Q11. Deactivated and deleted

Question: Jordan has departed and his Okta identity is deactivated. A target deactivation request failed, and an application session still retrieves protected data. A colleague proposes deleting the Okta user to close the ticket. Why does deletion not resolve the missing evidence?

Read the teaching explanation

Explanation:

Deleting the Okta user is a separate, irreversible action. It does not supply a successful target correction or prove that the application stopped accepting the session.

Preserve the ability to identify the correct records while completing the access-removal requirement. The target account and session need their own verification. Removing an identity record cannot replace evidence that the specific exposure ended, so it should not become a shortcut around an unresolved departure.

Q12. Suspension and SCIM

Question: Support suspends a person’s Okta account. Projects uses an outbound SCIM integration, which manages application accounts separately, with deactivation implemented as active false. No target request is supplied. Does suspension alone establish that SCIM deprovisioning was sent?

Read the teaching explanation

Explanation:

No. Okta suspension alone does not send the outbound SCIM deprovisioning event. Inspect the supported lifecycle action and actual target request before reporting an application-account change.

SCIM is an account-management interface, and the target state needs its own read. Here Projects deactivation would set active false and retain the resource. An Okta suspension cannot substitute for that operation or its result when the approved requirement calls for downstream access removal.

Prepare the intended joiner outcomes

Q13. Connect the joiner chain

Question: A company approves Maya’s employment and the point when her work access may begin. It must establish her identity and prepare the applications needed for her job. Which outcomes belong in a reasoned statement that this joiner is ready?

Read the teaching explanation

Explanation:

Start with approved employment and the effective access point. Verify the correct source record, matching and identity, intended activation and authentication readiness, groups and assignments, and required target accounts, sign-in, and permissions.

These are connected dependencies, not a guaranteed connector execution order. The evidence should show that Maya can perform her intended work. A successful early step helps locate progress, but it cannot supply the later results that readiness still depends on.

Q14. HR arrived and Okta Active

Question: A new employee’s HR record has arrived and their Okta identity is ACTIVE. Their approved access-start time, application assignments, target accounts, sign-in, and required work permissions remain unchecked. Is “ready to work” established by the two supplied observations?

Explanation:

Not yet. The observations establish the received HR record and enabled Okta account. They leave the approved effective access point and required application outcomes unverified.

Report those completed findings, then ask for the missing assignment, account, sign-in, and permission evidence. Readiness is a business outcome across the required scope. A person can be prepared in one system while still being unable, or not yet authorized, to perform the intended work.

Q15. Preparation before a future start

Question: An employee is approved to begin work next Monday, and HR records that future-dated start today. Preparation may occur before Monday, but no separate approval for earlier working access is supplied. Does today’s record arrival authorize immediate use?

Read the teaching explanation

Explanation:

No. Preparation and permission to use access are separate decisions. The supplied approval makes Monday the effective access point; today's data entry does not change it.

Check that the configured process respects that distinction, then verify the required outcomes at the appropriate time. Having the record available can support preparation without establishing immediate authorization. Always read the approved timing rather than assuming the arrival timestamp determines when working access should begin.

Q16. Existing account at joining

Question: A company approves a new employee’s start. An application already contains a plausible account with their name, but ownership and any existing Okta identity relationship are unknown. Should support immediately create another identity or account to finish preparation?

Read the teaching explanation

Explanation:

First investigate ownership and matching. The plausible account may belong to the person, to someone else with the same name, or contain data that needs review before a relationship is accepted.

Creating another identity or account without checking can leave duplicate or unmanaged paths. The approved start defines the goal, but it does not identify every existing record. Establish the intended association before choosing the account operation, then verify the resulting preparation.

Q17. Priya’s joiner and end condition

Question: Priya is a contractor under a sponsor-approved process that manages her profile in Okta and specifies an access end condition. Employee profiles use Workday and AD, but Priya is excluded from those imports. Must she acquire those source associations to be prepared correctly?

Read the teaching explanation

Explanation:

No. Use Priya's approved contractor process, information, maintenance responsibilities, and agreed end condition. Adding employee-source associations merely to copy another population's journey would conflict with the stated model.

Her application assignments, target accounts, and actual access still need verification. A different maintenance path changes how preparation is governed, rather than removing the need to check its outcomes. Start with the intended population and approved responsibility, then follow the appropriate records.

Define what a move changes and preserves

Q18. Read the approved move

Question: Maya’s approved move from Sales to Finance is effective. She remains employed as NB-1042. Sales-group membership and Salesforce access must end with no transition exception, while her existing Projects account and access must continue with department code FIN instead of SAL. Which outcomes should support remove, update, and preserve when evaluating this mover?

Read the teaching explanation

Explanation:

Read the move as three kinds of work. Remove the obsolete Sales membership and Salesforce access. Update the governed department to Finance and Projects' department code to FIN. Preserve Maya's existing identity, intended Projects account and continuing Projects access.

Those are parts of the same approved outcome. Adding the new department without ending the old access would be incomplete. Disabling everything would also be wrong because Maya must keep working in Projects.

Use this requirement to judge each observed result. It tells you what to end, what to change and what to retain; the department name alone does not supply every role or permission decision.

Q19. Finance does not mean manager

Question: Maya’s approved move changes her department to Finance and preserves Projects access. Daniel, another Finance employee, is a manager with Expense approval permissions. No manager role or approval requirement is supplied for Maya. Does her department change establish Daniel’s capabilities for her?

Read the teaching explanation

Explanation:

No. A department value does not establish every role held by people in that department. Maya's approved responsibilities determine which capabilities she should receive or retain.

If expense approval is required, obtain that business authorization and relevant application permission evidence. Daniel's access is an example of another person's role, not an authorization rule for Maya. Correct profile data is useful, but it cannot supply an unstated manager entitlement.

Q21. The remaining assignment path

Explanation:

Picture the two routes separately: membership supplied a group route to assignment, and the individual assignment supplied another route. Ending the first did not remove the second. The rule can have done its job while the application assignment remains.

Address the surviving individual assignment under the approved removal process, then verify the required application outcomes. Changing the correct Finance data or the working Sales rule would leave the demonstrated assignment problem unanswered.

Together the findings show an unjustified surviving assignment and application entry contrary to the approved move. No corrective follow-up is supplied, so removal is not yet verified. A demonstrated discrepancy and a supported next action are useful findings, but they do not mean the correction has already occurred.

Follow a departure across systems

Expense’s account-removal method and the session’s persistence mechanism are unknown. Which supplied findings are completed, and which departure outcomes remain outstanding?

Read the teaching explanation

Explanation:

The supplied Okta deactivation and assignment removal are complete, and the linked AD account's disablement is independently verified. Those successes remain valid.

Projects still reports an active account after its failed request, and Expense still accepts the checked session. Both need separate application follow-up. A completed initiating-system action does not supply every target result, so the broader departure remains open despite the meaningful work already verified.

Q28. Fresh Okta sign-in blocked

Read the teaching explanation

Explanation:

No. The Okta test asks whether Jordan can start a fresh Okta sign-in. The Expense observation asks whether that application still accepts a session it already established. Different services can give different answers to those two questions.

Both results are supplied: fresh Okta sign-in is blocked, and a new protected Expense response succeeds through the checked session. Repeating the Okta test would not cancel the application's observation.

Keep the completed Okta result and ask the Expense owner to resolve and verify its access-removal outcome. You do not need to explain the session's persistence mechanism to recognize that this separate access still works.

Evidence and scope for closure

Keep the account and session identifiers with their owners and results. A further Okta success would still leave these particular target findings to verify.

Choose actions for current approval and state

Q41. Password, authenticator, lifecycle

Q42. Report partial completion clearly

Explanation:

Try: “Okta deactivation and the checked AD disablement are confirmed. The Projects account correction is verified. Expense's session outcome still awaits application-owner verification, so all required access removal is not yet established.”

That preserves completed work and identifies the remaining responsibility.
