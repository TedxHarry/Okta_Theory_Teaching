Day 2: Questions

Requests, participants, and protected communication

Q01. Request and response

Question: Devi opens Expense, a company application for handling expenses, in her web browser. The browser asks the application for a page, and the application replies with that page. Which message is the request and which is the response?

Read the teaching explanation

Explanation:

The browser's message asking for the page is the request. Expense's reply is the response.

Think of the exchange as a short conversation: “Please give me this page,” followed by the application's answer. The request tells us what was asked; the response tells us how the receiving system handled it.

Read the two together. A reply makes more sense when you know which system answered and which operation it was being asked to perform.

Q02. Client and server

Question: Devi’s browser sends a web request to Expense, a business application running on company servers. Expense handles the request and replies. Which participant is the client and which is the server? Do those labels describe Devi’s account state?

Read the teaching explanation

Explanation:

The browser is the client making this request. The receiving Expense system is the server handling it. These names describe roles in the exchange, not whether Devi's account is enabled.

The server might return a page, direct the browser elsewhere, or refuse the operation. Naming the participants helps you follow where the message went and which system produced the result.

Account state and usable access still need their own evidence. A client/server label does not supply them.

Q03. A client without a browser

Question: A configured software connection sends a request to a business application to update employee Devi’s account. Devi does not open a browser or carry the message. Can this still be a client/server exchange?

Read the teaching explanation

Explanation:

Yes. Software other than a browser can be a client. Here the configured connection sends the request, and the application acts as the receiving server.

The systems can communicate directly for their supported account-management work. Devi does not need to visit a page for that request to occur.

Identify the sender, destination, and purpose. An account update and a browser sign-in can both use requests and responses while doing different work and needing different result evidence.

Q04. One screen, several exchanges

Question: Devi uses a web application that loads a page, retrieves data, and submits a form. The page appears as one screen to her. Is that enough to treat everything she sees as the result of one HTTP request?

Read the teaching explanation

Explanation:

No. HTTP is the protocol used for web requests and responses, and one visible page can involve several of those exchanges.

The page might load successfully while a later data request or form submission fails. Both observations can be true without contradiction.

Find the request relevant to the reported problem and the response belonging to it. The screen is Devi's overall experience; the individual exchanges show which parts of that experience worked.

Q05. HTTPS and application access

Question: Devi opens a business application using an HTTPS address. No authentication result, application permission, or completed business action is supplied. What does protected communication tell you, and can it establish those other outcomes?

Read the teaching explanation

Explanation:

HTTPS protects communication in transit. It does not by itself establish who successfully signed in, what that person may do, or whether a business action completed.

A protected connection can carry a sign-in form, a successful result, or a refusal. The content and receiving system's decision still matter.

Keep the transport property separate from the application result. To claim a completed task, inspect the relevant request, response, and actual outcome rather than rely on the address starting with HTTPS.

Read the destination

Q06. Read the address

Question: A browser requests the fictional expense-application address https://expenses.northbridge.example/start?view=home. A URL describes a web destination and request information. Identify its scheme, host, path, and query parameter, and explain the job of each.

Read the teaching explanation

Explanation:

Start at the left. The scheme is https: the browser will use an encrypted HTTP connection. Next comes expenses.northbridge.example, the host it will contact. The /start path names what it requests at that host. After the question mark, view=home supplies a query parameter named view with the value home.

You can read the address aloud as, 'Contact this host using HTTPS, request /start, and send view set to home.' That describes the request without needing to memorize the whole address.

Now wait for the reply. Sending directions to a server does not tell us whether it returned the page Devi expected or accepted her sign-in.

Q07. Which host replied?

Question: Devi’s company uses an identity service to handle sign-in and a separate Expense application for business work. The identity-service page loads successfully, but Expense later refuses its request. Why must support identify the responding host for each result?

Read the teaching explanation

Explanation:

A host names a destination in the web exchange. These two results came from different systems handling different requests.

Loading the identity-service page does not establish Expense's later acceptance. Both the page success and application refusal may be accurate observations.

Attach each result to its host and purpose. Then follow the progress into the refused request and obtain the evidence needed there, rather than choose one general success or failure for the whole journey.

Q08. Path and query

Question: A browser requests https://reports.example/reports?department=Finance from a business application. How do the /reports path and department=Finance query parameter contribute different information, and do they establish what the server decided?

Read the teaching explanation

Explanation:

The path identifies the requested resource or operation at that host. The query carries additional information: the parameter department has the value Finance.

Those pieces describe the request, not a complete account of the server's response. The application could handle the supplied parameter in different ways according to its design.

Read the reply before claiming an outcome. A requested view or submitted value is not automatically a stored change or an accepted permission decision.

Q09. A department in the URL

Question: Devi’s browser sends a business-application request whose URL includes department=Finance. No update operation, response, or account read is supplied. Does that parameter prove her stored department was changed to Finance?

Read the teaching explanation

Explanation:

It proves that the request carried Finance as query information. It does not establish that the application changed Devi's stored account data.

The parameter might select a view or have some other supported purpose. Its presence alone does not choose the server's behavior.

For a stored-change claim, inspect the relevant operation result and intended account afterward. Keep the observation narrow, then ask what evidence would show what the receiving application actually did.

Q10. A similarly named environment

Question: The company keeps separate test and production instances of Expense. Devi reports a failure in production, the live business environment. Support finds a successful response from test but no result for her production attempt. Can the test success settle her report?

Read the teaching explanation

Explanation:

No. It establishes the checked request's result in test. Production has separate configuration, records, and attempt evidence.

The test success may help with a comparison once the relevant differences are understood. It still cannot replace Devi's production result.

Identify the intended instance and actual attempt before using evidence. Similar application names do not make two environments one destination.

What the messages ask and report

Q11. GET and POST

Question: A support analyst examines two HTTP messages to a business application, one using GET and one using POST. At a general level, what do those methods ask the server to do, and what else identifies the actual business operation?

Read the teaching explanation

Explanation:

GET generally requests a resource such as a page or information. POST submits information for processing.

The destination, endpoint, content, and purpose still matter. An endpoint is an address for an operation; a POST to a sign-in form asks for different work from a request to create an account.

Treat the method as one part of the message. It does not identify every business task or establish that the task succeeded.

Q12. Does POST mean account creation?

Question: An activity record shows that software sent an HTTP POST to a business application. The endpoint, request content, response, and target account have not been inspected. Can support conclude an account was created?

Read the teaching explanation

Explanation:

No. POST alone does not establish that account creation was the requested operation. Even a confirmed create request would still need its result checked.

Identify what was sent and which endpoint handled it, then inspect the response and relevant target record. Sending and successful completion are different observations.

Do not combine purpose and success into one method name. The business task and its outcome need their own evidence.

Q13. Headers and body

Question: A web message has headers and a body. For example, a redirect reply contains a Location header, while another reply carries page content in its body. How do headers and body serve different jobs?

Read the teaching explanation

Explanation:

Think about the reply in two parts. The headers describe the message or supply instructions. The body carries its content, such as the page the browser displays.

In this redirect example, the Location header says where the browser should go next. In the other reply, the page content is in the body. A refusal could also include explanatory text there, so the body can help us understand what happened.

Neither part replaces the other. Read the relevant headers and content beside the request they answer, rather than trying to infer the whole result from a single field.

Q14. Read the request line

Question: A fictional expense application receives this simplified request: GET /start?view=home HTTP/1.1 with Host: expenses.northbridge.example. What do these lines describe, and is HTTP/1.1 a result saying the user authenticated?

Read the teaching explanation

Explanation:

They describe the method, requested path and query, HTTP version, and destination host. Together they identify what resource was requested from which system.

HTTP/1.1 names the protocol version used in this example. It is not an account state or an authentication result.

Now read the response for this request. The request lines give that result context, but they cannot prove a later sign-in or business action completed.

Follow the redirect

Q15. Read a redirect reply

Question: Devi’s browser asks Expense, a business application, for its start page. Expense replies 302 Found with Location: https://identity.example/signin, a company identity-service address. What instruction does the reply give, and what is not yet verified?

Read the teaching explanation

Explanation:

It directs the browser to the address in Location. That is a redirect: a response telling the browser where to go next.

The instruction does not establish that the next page responded, that Devi completed sign-in, or that any account was created. Those are later results to inspect.

Follow the exchange as a conversation: the browser asks for Expense's page, and Expense supplies another destination. The next request and its reply remain separate evidence.

Q16. Who makes the next request?

Question: In a browser-based sign-in journey, Expense replies to Devi’s browser with a redirect to the company’s identity service. In this stated flow, who sends the next web request: Expense or the browser?

Read the teaching explanation

Explanation:

The browser makes the next request. Expense replies to it with a direction: 'Visit the identity service at this address.' The browser follows that direction.

Trace three messages: the browser asks Expense, Expense replies to the browser, and the browser asks the identity service. Keeping the browser in the middle helps explain why Devi sees the destination change.

A separate account-management connection could send a request directly between systems. That is different work. Following this redirect does not show that either system created or updated Devi's account.

Q17. Redirect or provisioning?

Question: Devi’s browser follows a redirect from a business application to the company identity service. No account-management operation or target-account record is supplied. Does the successful browser movement prove the application created her account?

Read the teaching explanation

Explanation:

No. It demonstrates the observed movement to another web destination. Account creation needs a relevant account-management operation and result.

A redirect asks the browser to visit an address. Provisioning is work to create or maintain an account through a supported process, which may happen separately between software systems.

Both can support the same person's access, but success in one does not establish the other's completion. Identify the work the message actually requested.

Q18. The redirect succeeded; did the journey?

Question: A browser receives a 302 redirect from one server to another address. No evidence shows the next request or the next server’s response. What progress can support report without claiming the whole web journey succeeded?

Read the teaching explanation

Explanation:

Report that the first server returned the redirect instruction. The next destination's result remains unverified.

The browser may be expected to follow it, but an expected next step is not an observed completion. Obtain the next request and response if that stage matters to the problem.

This describes useful progress accurately: the journey has a confirmed direction. It does not yet have a confirmed final result.

Successful steps and refused requests

Q19. A successful sign-in form

Question: Devi requests a sign-in page from the company’s identity service. It returns HTTP 200 with a form, but she has not submitted credentials or completed another authentication interaction. Did loading the form or authenticating Devi succeed?

Read the teaching explanation

Explanation:

The form loaded successfully. Devi has not completed authentication in the supplied example.

Ask what the server was asked to do: return a sign-in page. The 200 response reports success for that request. Returning a form that asks for identity proof is different from checking the proof Devi later provides.

To say she authenticated, look for the result of that later interaction. The useful reading is 'the sign-in form loaded,' rather than 'every part of sign-in and application access worked.'

Q20. A 200 response with an error page

Question: Devi requests a business-application page. The HTTP response is 200, but the returned page describes an application-level problem and her intended task is not completed. Should support ignore the page because the status looks successful?

Read the teaching explanation

Explanation:

No. Read the status and the returned content together. A server can deliver a page successfully while that page reports a problem with the business goal.

Identify the intended operation and the application-level result. The status supplies information about the particular request, not a guarantee of every outcome Devi wanted.

The response body is evidence too. Disregarding it because of one number can hide the detail needed to explain the user's experience.

Q21. What does 403 explain?

Question: Expense, a business application, returns HTTP 403 and “We could not accept the sign-in information” for Devi’s request. No detailed rejection reason is supplied. Are wrong password, missing permission, or malformed sign-in information confirmed causes?

Read the teaching explanation

Explanation:

The request was refused, and the text reports a sign-in-information rejection. It does not establish which of those proposed causes explains it.

Ask for the detailed application rejection and the corresponding exchange for this person, instance, and attempt. Those records help distinguish the alternatives.

The refusal is a finding. Its root cause, the underlying reason for it, remains unresolved. Choosing a familiar fix now would add certainty the generic message does not provide.

Q22. Where observed, where caused

Question: In a correlated browser sign-in attempt, the identity-service steps succeed and a business application is the first system shown refusing the arriving information. No detailed rejection analysis is supplied. Does that prove the underlying defect originated inside the application?

Read the teaching explanation

Explanation:

It tells us where the failure became visible. It does not yet tell us where the cause began.

The application may have received information it could not accept, or its own checking configuration may disagree with that information. Both are possibilities here. A rejection alone does not choose between them.

Ask for the application's detailed rejection and the corresponding sign-in information for this attempt, then compare them with its requirements. That turns 'the app showed an error' into a question we can investigate without blaming a system before the evidence supports it.

Read an event in context

Q23. Read JSON structure

Question: An event is stored as JSON, a structured text format. The selected excerpt is {"actor":{"displayName":"Devi Rao"},"target":[{"displayName":"Expense"}]}. What do braces and square brackets tell you, and where do the two display names belong?

Read the teaching explanation

Explanation:

Start with actor. Its value is inside braces, so it is an object: a group of related named details. Inside it, displayName has the value Devi Rao.

Now move to target. The square brackets mean it holds a list. This list contains one object, and that object's displayName is Expense. The same field name appears twice, but its position tells us whether it describes the actor or a target.

You can read this as, 'The actor shown is Devi Rao, and the target shown is Expense.' The excerpt does not include an action or outcome, so we cannot add 'sign-in succeeded' to that sentence. Reading the structure helps us find information; it does not fill in information that is missing.

Q24. Translate the event

Question: Okta is the company’s identity service. Its selected event fields show eventType = user.authentication.sso, actor Devi Rao, target Expense, and outcome.result = SUCCESS. SSO means single sign-on. No application acceptance or attempt-correlation evidence is included. Translate the record into one careful sentence.

Read the teaching explanation

Explanation:

Try: “Okta recorded a successful application single-sign-on event associated with Devi Rao and Expense.”

That names the recorded action, actor, target, and result. It does not add Expense acceptance or identify which of Devi's possible attempts the event belongs to.

Next, obtain the identifiers, timing, and relevant application records if the ticket needs those outcomes. A clear sentence makes the record useful without extending its evidence beyond the selected fields.

Q25. Who is the actor?

Question: Alex is an administrator who updates employee Devi’s account. The resulting account-maintenance event includes actor and target fields. Must actor name Devi because the support ticket concerns her?

Read the teaching explanation

Explanation:

No. Actor describes who or what performed the recorded action. In this supplied situation, Alex performs it; Devi's account is the affected record.

An automated process could also be an actor in another event. Read the actual entries and surrounding context rather than assigning roles from the ticket title.

This distinction prevents an administrator's maintenance action from being mistaken for Devi's sign-in. The person with the problem is not always the person or software that acted.

Q26. A target list

Question: A support analyst reads one selected Okta event whose target list contains a single application entry. The full target structure of other events has not been inspected. Does this establish that every event has exactly one target?

Read the teaching explanation

Explanation:

No. A target list can contain several affected objects. One selected entry does not define every event's contents.

Inspect the relevant event and identify which entries answer the investigation question. Display names can orient you, while available identifiers and context distinguish the actual objects.

The example supplies one observed list, not a universal limit. Reading the record field by field keeps its particular contents separate from assumptions about other occurrences.

Q27. The meaning of outcome.result

Question: For one explicitly correlated attempt, Okta records a single-sign-on event with outcome.result = SUCCESS, then Expense refuses the arriving sign-in request. Okta and Expense are separate services. Does the success erase the refusal?

Read the teaching explanation

Explanation:

No. Outcome.result belongs to the action recorded by that event. Expense's refusal belongs to a separate application request.

Both can be correct: the identity service reports its successful SSO step, while the application rejects the information it receives afterward.

Preserve both observations and inspect the exchange at that boundary. Discarding the refusal would hide why the overall business goal is unfinished. One recorded success is not a result for every later system.

Q28. A selected excerpt is incomplete

Question: Devi reports a failed Expense attempt. A selected event excerpt names Devi and Expense but provides no usable time, full identifiers, or request context. Does it independently establish that the event belongs to her reported attempt?

Read the teaching explanation

Explanation:

No. It supplies selected details, not a verified relationship to this attempt. Devi may have opened the same application more than once.

Obtain timing, identifiers, and request context that connect the actual records. Display names alone may not uniquely identify either the objects or the activity.

If a case explicitly supplies correlation, use it. Here that relationship is absent, so leave it unverified instead of building one story from familiar labels.

Connect the right evidence

Q29. Someone else succeeded

Question: Devi reports that Expense refused her sign-in. Support finds a successful event for Priya, a different user, accessing Expense. No result tied to Devi’s attempt is supplied. Does Priya’s success resolve Devi’s complaint?

Read the teaching explanation

Explanation:

It supplies a result for Priya, not Devi. It cannot establish Devi's acceptance or disprove her refusal.

The event might be useful comparison evidence once the relevant context and requirements are understood. It still cannot replace records for the affected person and attempt.

First connect evidence to the intended identity and activity. A search full of successes does not mean every user's request must have worked.

Q30. Same person, another application

Question: Devi reports failed entry to Expense. A successful event names Devi but targets a different business application. Expense’s own result has not been checked. Can the event be used as Expense acceptance evidence?

Read the teaching explanation

Explanation:

No. The person matches, but the target and operation do not. The event describes its own recorded action.

Find the intended Expense instance and the corresponding result for the reported attempt. An actor name is only one part of the connection.

Carry the whole context with the outcome: person, application, activity, and time. Matching a familiar field does not turn unrelated evidence into confirmation of this ticket.

Q31. Same person and app, another time

Question: Two records mention Devi and Expense. Their displayed clock times look similar, but their time zones, attempt identifiers, and sequence have not been compared. May support treat them as one attempt solely from that appearance?

Read the teaching explanation

Explanation:

No. Devi may have tried Expense more than once. Two familiar names and similar clock displays do not tell us which attempt each record describes.

Check the time zones as well as the clock times. UTC is a common reference time; UTC+02:00 means two hours ahead of it. For example, 09:00 UTC and 09:00 UTC+02:00 are different moments even though both displays say 09:00. Then compare the available attempt or request identifiers and the sequence of events.

Correlation means establishing that these records belong to the same activity. If the available evidence does not establish that connection, keep it open. We should not borrow a success from another attempt to explain the one that failed.

Q32. Do both systems share one ID?

Question: Okta and Expense keep separate records of a user’s sign-in journey. Their event identifiers may use different formats. Must they automatically share one identical ID before support can relate the observations?

Read the teaching explanation

Explanation:

Do not assume a common identifier. Depending on the available evidence, request context, application references, timing, and sequence may support the relationship.

Use the values actually supplied by the systems. If the connection cannot yet be established, record that missing correlation rather than invent an identical ID.

The goal is a justified relationship between occurrences. Different identifier formats neither automatically disprove a link nor prove one.

Q33. Searching only for failures

Question: In one correlated Expense sign-in journey, successful Okta authentication and single-sign-on steps precede an application refusal. System Log is Okta’s event record. Why could a search showing only failure outcomes miss useful evidence?

Read the teaching explanation

Explanation:

It can hide the successful steps that establish how far the journey progressed. Those results do not close the ticket, but they help locate the later failure boundary.

Choose the person, application, time window, and relevant actions rather than remove everything labeled success. Then combine the Okta records with the application's own rejection evidence.

A useful search answers the sequence question. The identity service may not hold the full detail of a refusal made by another application.

Q34. An empty search

Question: Support searches Okta’s System Log for Devi’s reported Expense sign-in and finds no matching event. The time range, time zone, filters, and identifiers have not been verified against the report. Is the attempt proven never to have occurred?

Read the teaching explanation

Explanation:

No. The finding is that this query did not locate a match within its selected scope. The query may not yet fit the reported activity.

Check timing, zones, filters, identifiers, and available application evidence before making a broader absence claim.

An empty search and a confirmed absence are different observations. Keeping that distinction helps you refine the next check instead of using a limited result to dismiss the user's report.

Accounts, sessions, and cookies

Q35. Account, session, and cookie

Question: A business application keeps Daniel’s user account, establishes a session after accepted sign-in, and uses a browser cookie to help recognize later requests. How are the account, session, and cookie different objects?

Read the teaching explanation

Explanation:

Daniel's account is the application's record about him. It can exist before he opens the website. After accepted sign-in, the session lets Expense recognize his ongoing interaction across requests. The cookie is data kept by his browser that can help Expense recognize those requests.

Imagine he opens another page in Expense during that visit. His browser can send the cookie with a matching request, and Expense checks the associated session. The browser-held value helps connect the request to the interaction; it is not Daniel's account record.

That distinction explains why deleting a cookie does not delete the account. It also explains why finding a cookie in the browser does not prove Expense still accepts the session. Check the object and result you actually want to know about.

Q36. Removing a cookie

Question: Daniel deletes a cookie used by Expense, a business application, from his browser. No account-deletion operation or application record check is supplied. A colleague says his Expense account was deleted. Is that supported?

Read the teaching explanation

Explanation:

No. Removing browser-held data does not delete the application's account record. It may change how that browser presents information on later requests.

To establish account deletion, inspect the relevant account-management operation and destination record. The cookie action supplies neither result.

Explain the change precisely: the browser removed data it held. The account is a separate object whose existence and state must be checked in the application.

Q37. A cookie is still present

Question: A browser still stores a cookie associated with an earlier sign-in session. No new server response or session-status evidence is supplied. Does the cookie’s presence prove the application continues accepting that session?

Read the teaching explanation

Explanation:

No. It establishes stored browser data, not the server's present acceptance decision. The session may have ended or expired, and not every cookie represents a sign-in session.

Inspect the relevant service result for the interaction being investigated. A new accepted request and a visible stored value answer different questions.

The browser presents information; the receiving service decides whether it remains valid for access. Do not substitute one side's storage for the other's result.

Q38. Two services, two session questions

Question: Devi has an accepted session with Okta, the company identity service. Expense is a separate application that can establish its own session after sign-in. No Expense session result is supplied. Does the Okta session alone prove she has an accepted Expense session?

Read the teaching explanation

Explanation:

No. The services can maintain separate session state. The Okta observation establishes its own result, not Expense's decision.

Obtain application evidence showing whether Expense accepted the sign-in and established or reused its relevant session. Record that outcome separately when it is supplied.

You do not need every expiry mechanism to apply the basic distinction. Attach each session result to its owning service and leave the other service's state unverified until evidence answers it.

Follow the operation to its result

Q39. Compare the two message flows

Question: A browser follows a redirect during sign-in. Separately, a configured connection sends an account-management API request to a business application. An API is an interface through which software requests information or operations. How do these exchanges differ in purpose and participants?

Read the teaching explanation

Explanation:

The redirect directs the browser to another address, continuing its web journey. The account-management request asks the target to perform work on an account and may travel directly between software systems.

Both can use web messages, but that does not make them the same operation. Follow the actual sender, destination, and requested work.

A successful browser step does not establish a successful account update. The result evidence needs to match the purpose of the request.

Q40. The account request was sent

Question: A configured software connection sends a request to create Devi’s account in a business application. The send is recorded, but no application response or target-account read is supplied. What is established, and what is needed before reporting creation succeeded?

Read the teaching explanation

Explanation:

The recorded request establishes an account-creation attempt for the supplied purpose. It does not establish the receiving application's result.

Obtain the response and relevant target record. The application might accept or reject the request; sending alone cannot distinguish those outcomes.

Describe the attempted work accurately, then verify the destination. A request/response habit is just as useful for account management as for loading a page.

Q41. Reconstruct Devi’s failed journey

Question: Expense is a business application connected to Okta for single sign-on (SSO). For one explicitly correlated attempt, Devi’s browser follows a redirect, the sign-in form loads, her required interaction succeeds, and Okta records SSO success. Expense then refuses the return request with 403. Where is the first demonstrated failure, and what evidence is needed next?

Read the teaching explanation

Explanation:

The first demonstrated failure is Expense's refusal of the return request. Earlier steps have their own successful observations.

Request the detailed application rejection and corresponding sign-in exchange for this same attempt. Those records can explain why the arriving information was not accepted.

The failure boundary is established, but its underlying cause is not. Preserve progress and refusal together. They identify a focused next question without proving that a password reset or any other particular correction is required.

Q42. Repair a misleading update

Question: For Devi’s identified attempt, Okta records successful single sign-on (SSO), but the connected Expense application refuses the corresponding request. No detailed cause, password reset, or successful follow-up is supplied. Rewrite: “Okta says SUCCESS, so Expense worked. We reset Devi’s password and closed the request.”

Read the teaching explanation

Explanation:

The note stretches one recorded success across the application boundary and invents an action and closure. The refusal remains part of the evidence.

Try: “Okta recorded SSO success for the checked attempt, but Expense refused its corresponding request. The detailed rejection and relevant exchange are still needed to identify the cause. No correction or successful follow-up is established.”

That gives the next owner a clear finding and evidence request without claiming the business goal was completed.

Name resolution and status meanings

Q43. A browser error before a connection

Question: Devi tries to open Expense at a named web address. The browser cannot resolve the host name to a network address and establishes no connection. No application response is obtained. Must the displayed browser error be an HTTP refusal sent by Expense?

Read the teaching explanation

Explanation:

No. DNS, the Domain Name System, helps resolve a host name to a network address. The supplied lookup failure happened before a connection was established, so no Expense HTTP response is demonstrated.

Investigate the name-resolution boundary instead of inventing a server status or permission denial.

A browser can display its own problem report without receiving a refusal from the application. Identify who produced the observed message before interpreting what it says about the destination.

Q44. Compare 400 and 401

Question: Support compares HTTP responses from two web requests: 400 Bad Request and 401 Unauthorized. No detailed cause is supplied. How do their general meanings differ, and does the word Unauthorized make 401 proof that the user lacks a business approval role?

Read the teaching explanation

Explanation:

400 indicates a problem with the request. 401 indicates a lack of valid authentication credentials for the requested resource. Despite its name, 401 concerns authentication, not proof of a missing business role.

Authentication asks about identity proof; an application role concerns what an identified person may do. Read the actual request and detailed response before choosing a correction.

The status helps classify the exchange. It does not supply every underlying cause or establish the user's approved capability.
