Day 3: Questions

Attributes, values, and profiles

Q01. Name the detail

Question: Daniel is an employee whose user profile stores named details about him. A selected field is "department": "Finance". Which part names the attribute, which part is its value, and what does that observation establish?

Read the teaching explanation

Explanation:

Department is the attribute name, and Finance is its value in this record. An attribute is one named detail about the person; its value is what this particular record supplies.

Think of the question “Which department?” The field gives a place for the answer, and Finance supplies that answer here.

The observation is scoped to this profile. Another application's account is a separate record that needs its own check before you claim it has the same department.

Q02. An attribute and a profile

Question: Daniel’s user profile contains first name Daniel, employee number NB-1020, and department Finance. How is the department attribute different from the profile as a whole, and why does the distinction help an investigation?

Read the teaching explanation

Explanation:

Department is one named piece of information. The profile is the collection of attributes, including the name, employee number, and department.

“The profile is correct” can hide which fields were actually inspected. A correct employee number does not prove that the department was checked too.

Name the representation and field: “Daniel's user profile contains department Finance.” That makes the observation easier to compare with other records and keeps unrelated fields outside the claim.

Q03. Active is not Finance

Question: Okta is a company identity service holding Daniel’s user account and its profile data. Support reads account status Active but does not read department. Is “His account is Active, so his department is correct” supported?

Read the teaching explanation

Explanation:

No. Active is an account-state observation. Department is a separate profile attribute, and its correctness needs the approved value and actual field to be compared.

A user object can include information outside its profile, such as account status and an object identifier. Those are not department values.

Read the relevant field directly. Enabling an account would not establish that an inaccurate department was corrected or that a mapping used the right input.

Q04. Make the observation precise

Question: Support checks employee Daniel’s central user profile in Okta, the company identity service, and reads department Finance. No application-specific profile or target account is inspected. Improve the note “Daniel looks right in Okta” without claiming more than was checked.

Read the teaching explanation

Explanation:

Try: “Daniel's central Okta user profile contains department Finance.” Include the relevant account identifier and check time if available.

That names the record, field, and observed value. The broader phrase looks right could accidentally include fields or other profiles nobody inspected.

An application-specific profile holds information prepared for an application, and its target account is another record. Both remain unverified here. Precision makes the next comparison possible without expanding the original finding.

Schemas and field requirements

Q05. Structure or stored value?

Question: A user-profile system defines employeeNumber as a supported text field, then stores NB-1020 for Daniel. Which question concerns the schema: “Is employeeNumber a supported text field?” or “What employee number does Daniel have?”

Read the teaching explanation

Explanation:

The first concerns the schema, which defines the fields and their constraints. The second concerns the value stored in Daniel's profile.

Think of a form's design and a filled-in form. The design specifies which answers can be recorded; the completed record supplies one person's answers.

Both matter. A suitable employee-number field does not establish that Daniel's value is present or accurate, while a readable value does not by itself establish every field constraint.

Q06. Adding a field

Question: An administrator adds a supported custom department field to a user-profile schema, the definition of allowed fields and constraints. No source values or maintenance process have been supplied. Does adding the field give every user the correct department?

Read the teaching explanation

Explanation:

No. It makes a place for information, not the correct information itself. Each user's value still needs an applicable source or maintenance process.

Imagine adding a department column to an empty employee list. The heading organizes where the answer belongs, but it cannot tell you which department each person has.

Plan how the field will be populated and verify the resulting profiles. Schema readiness and accurate user data are different outcomes.

Q07. Readable but unacceptable

Question: Projects is a fictional business application whose required departmentCode accepts only SAL for Sales, FIN for Finance, and IT for IT. Daniel belongs to Finance. Would the full text Finance be acceptable merely because a person can read it?

Read the teaching explanation

Explanation:

No. The field accepts text, but it also restricts which text is allowed. Finance is understandable to a person; FIN is the accepted code for this department in Projects.

Think of choosing from an agreed list. A full department name can express the right idea and still be outside the list. The mapping needs to preserve the idea while producing the accepted code.

For Daniel, leave the approved department as Finance at the source and prepare FIN for this destination. The difference in text is intentional. Sending the full name unchanged would not meet the supplied field requirement.

Q08. A required field

Question: Projects requires a departmentCode value for each account. The approved code for employee Daniel’s department has not been established, and his field has not been read. What does required tell you, and what does it leave unanswered?

Read the teaching explanation

Explanation:

Required is a constraint: the application expects a value in that field under its stated rules. It does not identify Daniel's legitimate department or show that a correct value was stored.

Obtain the approved input, accepted representation, and relevant resulting record. Filling the field with a guessed code can make it look complete while making it wrong.

The constraint helps define the investigation. It does not substitute for knowledge about the person.

Four records to keep separate

Q09. Place the four records

Question: Daniel has an employment record in Workday, his company’s HR system. Okta keeps his central user profile and information prepared specifically for his Projects assignment, called the Projects app user profile. Projects has its own account record. Where do those four records live?

Read the teaching explanation

Explanation:

Start by grouping the records by location. Workday holds the employment record. Okta holds two profiles: the central profile about Daniel and the Projects-specific app user profile. Projects holds its own account record.

The name app user profile can be misleading at first. Here, app tells you which application the prepared information is for. It does not move that profile out of Okta and into Projects.

So a value read from that profile supports a statement about what Okta holds for the assignment. To say what Projects stores, inspect the linked account there. Keeping those two locations clear helps you avoid stopping at a prepared value before checking the destination.

Q10. Why prepare another profile?

Question: Okta holds Daniel’s central department as Finance. Projects, a separate business application, expects departmentCode FIN. Why prepare an application-specific user profile in Okta instead of assuming the central profile is enough?

Read the teaching explanation

Explanation:

Different applications can need different field names and formats. The app user profile represents the information for this particular application assignment.

Here it prepares departmentCode FIN from the central Finance value. Another application could have different requirements without changing Daniel's department.

Preparation is not delivery. The configured account-management process must still send the intended information, obtain a result, and leave the correct value in the target account.

Q11. Prepared is not stored at the target

Question: Daniel belongs to Finance, which Projects represents as FIN. His Projects app user profile (the application-specific information stored in Okta) contains FIN. No update response or account read inside Projects is supplied. Can support report that Projects stores FIN?

Read the teaching explanation

Explanation:

Report the prepared FIN value in Okta, not a verified Projects value. The target account is a separate record whose state has not been inspected.

Request the relevant operation result and the linked account in Projects. The value can be prepared correctly while delivery remains unfinished or unknown.

This distinction prevents stopping at the wrong layer. A profile named for an application does not mean it is the application's own stored record.

Q12. Do not infer account creation

Question: Okta holds a Projects app user profile for Daniel’s assignment. This is information prepared in Okta for a separate business application. No account-create result or target record is supplied. Does its visibility prove Projects created Daniel’s account?

Read the teaching explanation

Explanation:

No. The visible app user profile establishes the prepared representation in Okta. It is not a receipt for creation inside Projects.

Inspect the relevant account-management operation and intended target record before claiming creation. Verify the association rather than selecting a similarly named account.

Preparing information, sending an operation, and storing an account are distinct observations. They can be connected by the design while still requiring their own result evidence.

What a mapping defines

Q13. Explain a mapping

Question: Workday records Daniel’s department as Finance, Okta represents it in a central profile, and a separate Projects application requires the code FIN. How would you explain the attribute mappings between those fields without writing a formula?

Read the teaching explanation

Explanation:

You could say, 'A mapping tells us how to take information from one named field and represent it in another.' One mapping represents Workday's department in Daniel's central Okta profile. Another prepares the code Projects expects.

The first can preserve Finance as Finance. The second needs to turn Finance into FIN in the Projects-specific profile held in Okta. Those are two relationships with different destinations, so name which one you mean.

The rule explains the intended conversion. To find out what actually happened, follow the relevant import or update and read the resulting records. A written conversion rule is not a completed account update.

Q14. The rule and the fresh data

Question: Workday is the company HR system and Okta holds its central user profiles. A mapping is configured to represent Workday department in Okta. No recent import result or destination read is supplied. Does the configured rule prove fresh information was retrieved?

Read the teaching explanation

Explanation:

No. The mapping defines the field relationship; it does not itself retrieve new information or prove an import completed.

An import brings source records or changes into processing. Check that applicable operation and the resulting user profile when freshness is the question.

Keep the rule and execution apart. Knowing how a value should be represented locates the next investigation, but it cannot establish that the latest input arrived.

Q15. Name the destination

Question: A diagram maps Daniel’s central Okta department to departmentCode in his Projects app user profile, which is held in Okta. The diagram does not show a target update. Improve “Okta department goes to Projects” so the destination is precise.

Read the teaching explanation

Explanation:

Say: “The central Okta department supplies departmentCode in the Projects-specific app user profile held in Okta.”

Then describe delivery to the account inside Projects as a separate configured operation that needs verification.

The extra detail prevents a calculation arrow from becoming an account-update claim. The prepared value and the application's stored value are different records, even though both concern the same person and application.

Choose the direction

Q16. App to Okta

Question: In Okta’s mapping interface, an upstream HR integration supplies employee values toward the Okta user profile. Another connection prepares values for a downstream business application. Does the direction label App to Okta necessarily name the application the employee is trying to open?

Read the teaching explanation

Explanation:

No. App in this interface can refer to an upstream source integration or directory as well as a business application.

App to Okta describes values coming from that connected integration toward the Okta user profile. Identify the actual connection and fields before interpreting the direction.

The label describes a relationship, not a universal application identity. Reading the wrong integration can leave the real discrepancy unexplained.

Q17. Does the reverse exist?

Question: A company maps an employee’s department from its Workday HR record into an Okta user profile. Only that incoming direction is supplied; no reverse operation is shown. Does it automatically define or authorize an Okta-to-Workday department update?

Read the teaching explanation

Explanation:

No. A rule in one direction does not automatically define its reverse or authorize a write back.

Inspect the reverse relationship, supported operations, and actual configuration if that action is being considered. Do not invent continuous two-way synchronization from one arrow.

The habit is simple: identify where this value comes from, where it is meant to go, and which operation uses the rule. Reverse movement needs its own agreement and evidence.

Q18. Choose the relevant relationship

Question: Daniel’s approved Finance department is correct in Workday and his central Okta profile. Projects expects FIN, but its application-specific profile held in Okta contains SAL. Which field relationship should support inspect first, before a cause is confirmed?

Read the teaching explanation

Explanation:

Inspect the outgoing central-Okta-to-Projects-app-profile mapping. The supplied discrepancy is between a correct central input and the wrong prepared code.

The incoming HR-to-Okta result already agrees with the approved department. Inspecting only that relationship would leave this boundary unexplained.

Read the actual outgoing rule and evaluate its input. This selects a focused investigation; it does not yet prove which configuration or processing condition caused the stored discrepancy.

Q19. Mapping is not constant synchronization

Question: A mapping correctly defines how an HR department becomes an application code. No fresh import, recalculation, update response, or target read is supplied. Does the correct rule prove every connected record always has the latest value?

Read the teaching explanation

Explanation:

No. A mapping defines representation, while supported operations and update settings determine when it is used. Actual results establish whether the current value arrived.

An existing account can still hold old information. Obtain the relevant source, calculation, stored app-profile, operation, and destination evidence as needed.

The configured rule is useful, but it cannot certify steps nobody observed. Continuous synchronization should not be assumed merely because the conversion is correct.

Represent the same meaning

Q20. Different text, same meaning

Question: Workday, a company HR system, stores Daniel’s department as Finance. Projects stores FIN, and its approved code table defines FIN as Finance. Must one record be wrong because the text differs?

Read the teaching explanation

Explanation:

They can both be correct. The systems use different representations for the same business meaning under the supplied table.

Compare meaning and the destination's accepted format instead of requiring identical strings everywhere. Copying Finance into a field that accepts FIN could actually violate the application's requirement.

A useful comparison includes the rule explaining the code. Different text alone is not evidence that Daniel belongs to different departments.

Q21. Predict several outputs

Question: Projects accepts SAL for Sales, FIN for Finance, and IT for IT. The company requires missing or unrecognized departments to be reviewed rather than assigned a guessed code. Predict each known output and explain whether this written requirement automatically creates a review ticket.

Read the teaching explanation

Explanation:

Sales should produce SAL, Finance FIN, and IT IT. Missing or unrecognized input needs the stated review handling rather than a guessed department.

A calculation formula does not automatically create a ticket just because the business requirement says review. That workflow needs its own defined mechanism and owner.

Test the shared conversion across supported inputs and its handling boundaries. A single good Finance output does not establish every case.

Q22. Transformation or delivery?

Question: Daniel’s central department is Finance. Projects requires FIN, so a rule calculates FIN in an application-specific profile held in Okta. No target operation is shown. How does this transformation differ from delivering the code to Projects?

Read the teaching explanation

Explanation:

Transformation is the conversion from one representation to another: Finance becomes FIN according to the approved requirement.

Delivery is the configured operation that sends the prepared value to the application's account and obtains a result. The calculation can be right while that operation remains unverified.

Report both stages separately. What was calculated, what was sent, and what the target stored are related questions with different evidence.

Q23. Plain-language logic and expressions

Question: An administrator writes the business requirement “If department is Finance, produce FIN; if an input is unknown, flag it for review.” Okta Expression Language is the syntax used for supported calculation formulas. Is this sentence executable code, and does it implement review automatically?

Read the teaching explanation

Explanation:

It is plain-language logic, not ready-to-run Expression Language. It describes the intended conversion so people can agree on the outputs.

An expression needs the appropriate formula syntax. A review or notification process also requires separate implementation; the sentence does not create that action.

Agree on the business behavior first, then implement and verify the supported pieces. Understanding a requirement and deploying it are different outcomes.

Investigate the fixed-value defect

Q24. Locate the demonstrated defect

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. Workday and central Okta say Finance; the outgoing rule always returns SAL; preview, app user profile, and target show SAL. Where is the first demonstrated wrong representation?

Read the teaching explanation

Explanation:

Follow Finance from Workday into the central Okta profile. So far, the supplied values agree with Daniel's approved department. Now try that input in the outgoing rule: it returns SAL even though Projects requires FIN.

That is the first demonstrated wrong representation. A fixed-value rule always gives SAL; it is not choosing the code from Daniel's department. The preview shows the incorrect calculation, and the two later records also contain SAL.

Propose correcting that rule against the approved conversion while keeping the correct Finance input. The current snapshots do not tell us every past write that put SAL in Projects. We can establish today's calculation defect without inventing its full history.

Q25. Is the display lying?

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. The outgoing rule produces SAL from Finance, and Projects stores SAL and displays Sales according to its code table. Is the display itself shown to be the bad conversion?

Read the teaching explanation

Explanation:

The display agrees with the stored code: SAL means Sales under the supplied table. The problem is that SAL is the wrong code for Daniel's approved Finance department.

Follow the value backward. The supplied outgoing rule already makes the wrong conversion before the application displays it.

Changing a visible label would miss that demonstrated defect. Prepare the intended code, verify delivery, and check the stored and displayed result afterward.

Q26. Protect the correct source

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. The approved HR and central values are Finance, but a fixed outgoing rule always prepares SAL. Why would changing Workday to Sales be inappropriate?

Read the teaching explanation

Explanation:

Workday already records the correct business fact. Changing it to Sales would introduce a new error in the HR record rather than repair the faulty outgoing conversion.

The rule ignores the correct Finance input and returns SAL. Correct the relationship that conflicts with the requirement while preserving the legitimate department.

Making values agree is not enough if the agreement misrepresents the person. The correction needs to preserve meaning and satisfy the target's format.

Q27. A snapshot and a history

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. A current fixed-SAL rule previews SAL; the stored app user profile and target also hold SAL. No historical update sequence is supplied. Does this prove exactly which write put SAL in Projects?

Read the teaching explanation

Explanation:

No. It establishes the current calculation defect and observed values, not their complete history.

To identify the historical write, obtain the relevant operation evidence linked to Daniel's account and time. A plausible route through today's rule is not automatically a supplied past event.

You can still propose fixing the demonstrated rule. Keep that current finding separate from the unverified history so the recommendation does not claim more than the evidence.

Q28. A shared rule

Question: A shared Okta-to-application rule must convert Sales to SAL, Finance to FIN, and IT to IT; missing or unknown input needs review. Support proposes replacing a fixed-SAL rule after Daniel’s Finance case fails. Why check other users and inputs too?

Read the teaching explanation

Explanation:

The rule is shared, so its scope is wider than Daniel's account. A change that fixes Finance but breaks Sales or IT would not implement the full requirement.

Review the affected population, test each supported conversion and handling boundary, and plan how existing stored values receive the correction.

One person's ticket can reveal a shared defect. That does not make the correction private to that person or verify everyone else's resulting account.

Calculation and delivery

Q29. What the preview proves

Question: Projects requires FIN for Daniel’s Finance department. A proposed mapping is evaluated in a preview, which calculates an output for a selected input, and returns FIN. No saved configuration, stored-profile update, or target response is supplied. What has been demonstrated?

Read the teaching explanation

Explanation:

We can say, 'The proposed rule produced FIN when we tried Daniel's Finance input.' The preview demonstrates that calculation for that input.

Now separate trying the rule from applying it. The question does not say the configuration was saved, that the stored app user profile changed, or that anything was sent to Projects. A good preview cannot supply those missing results.

Keep the successful calculation, then check the applied configuration, stored app user value, update result and intended Projects account. That is how the answer moves from 'the rule looks right for this input' to evidence that Daniel's account was corrected.

Q30. Order the checks

Question: Okta prepares Daniel’s application-specific department code, and a configured update delivers it to a separate Projects account. Put these checks along the intended value journey: target read, mapping calculation, stored app user profile in Okta, account-update operation.

Read the teaching explanation

Explanation:

Start with the calculation, inspect the app user profile in Okta, follow the update operation, and read the target account afterward.

Each answers a different question: what the rule produces, what Okta holds for the assignment, what was attempted and accepted, and what Projects stores.

That is a way to organize evidence, not proof the process ran. Keep the records and operation linked to the same intended account when comparing them.

Q31. Correct preparation, old target

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. A preview calculates FIN and the stored app user profile holds FIN, but the linked Projects account still holds SAL. No update result is supplied. Which boundary remains unanswered?

Read the teaching explanation

Explanation:

Okta has the expected FIN value prepared, but the linked Projects account still holds SAL. The unanswered part is between those two records: what happened to the account update?

Ask whether that attribute can be updated through this connection and whether updates are enabled. Then look for Daniel's actual update: was it attempted, what value did it send, and what did Projects reply? Keep the account association with those checks so you know which record the request concerned.

An unattempted update and a rejected update would need different follow-up checks. Neither is established here. The correct preview and prepared value make this a delivery investigation; they do not prove a particular connector failure.

Q32. Do not invent the connector failure

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. Preview and app user profile are FIN, while Projects holds SAL. No update request or rejection is supplied. Can support conclude “The connector rejected FIN”?

Read the teaching explanation

Explanation:

No. A connector is the configured component used for the account operation, but this question supplies no rejection result from it or the target.

Obtain the relevant settings and update evidence. Disabled updates, an unattempted operation, or a recorded rejection would lead to different follow-up checks; none is selected here.

Describe the prepared/target discrepancy and missing operation result. A mismatch is evidence to investigate, not automatic proof of a particular component's failure.

Q33. Request useful evidence

Question: Daniel’s approved department is Finance. Workday is his HR system, Okta holds his central profile and a Projects-specific app user profile, and Projects keeps a separate target account. Projects requires FIN for Finance and SAL for Sales. The prepared code is FIN but the linked target account holds SAL, with no update result supplied. Which request is more useful: “Send screenshots” or “Show the value sent for Daniel’s linked account and the target’s reply”? Explain.

Read the teaching explanation

Explanation:

The second names the operation evidence needed at the unanswered boundary. It helps establish whether FIN was sent and how the receiver handled it.

Screenshots can be useful if they capture relevant facts, but the broad request leaves their purpose unclear.

Ask for evidence that distinguishes possible explanations rather than another unrelated profile view. A precise request identifies the account, value, and result that can change the investigation.

Q34. A request without its result

Question: Daniel belongs to Finance, and Projects requires the code FIN. A recorded update sends FIN to his correctly linked Projects account, but no reply or later target read is supplied. Is successful delivery and storage verified?

Read the teaching explanation

Explanation:

The evidence establishes an attempted update carrying the intended code. Acceptance and storage remain unverified.

Obtain the receiver's reply and the intended account's value after the operation. Sending FIN cannot decide whether the target accepted, rejected, or otherwise handled it.

Keep the attempt as meaningful progress without calling it a completed correction. The account-management result still needs evidence from the receiving side.

Verify and explain the correction

Q35. Recognize the complete follow-up

Projects requires FIN for Finance and SAL for Sales. The saved rule evaluates Finance to FIN; the app user profile holds FIN; a linked update reports success sending FIN; a later target read shows FIN displayed as Finance. What can support conclude?

Explanation:

Together, the observations support the checked department correction for Daniel. They connect the rule's output with the prepared record, successful operation, and actual target value.

The later read matters because it confirms what Projects stores and displays, not just what Okta intended to send.

Keep the scope: Daniel's linked account at the checked point. Sign-in, permissions, and outcomes for other users would need their own evidence if they belong to the requirement.

Q36. Daniel is not every user

Explanation:

No. The evidence verifies Daniel's account, not the entire population sharing the rule.

Other users need appropriately scoped checks, including their intended conversion and any existing values requiring updates. A correct rule does not itself demonstrate every stored target outcome.

Report the verified correction by person and account. Wider completion needs wider evidence, while Daniel's real success remains worth recognizing.

Q37. Explain the correction to Daniel

You could say: “Your HR record uses the name Finance. Projects requires FIN to mean the same department. The corrected conversion prepares that code, and the update and account check confirm Projects now stores FIN and displays Finance.”

That explanation connects each representation to its purpose without requiring formula syntax.

The destination claim is supported because the question supplies the update and read. A preview alone would not justify telling Daniel the target had already changed.

Missing and unrecognized input

Q38. Empty, null, and omitted

Question: A selected JSON excerpt of user data can show "department": "", "department": null, or omit department entirely. JSON is a structured text format. How do those representations differ, and does omission from the excerpt prove an empty full source field?

Read the teaching explanation

Explanation:

Read each form literally. Empty quotes mean a text value with no characters. The unquoted JSON value null marks no value in a field that is present. If department is omitted, this excerpt does not show the field at all.

Imagine receiving only a few lines from a larger record. A field missing from those lines might still be present in the full record. That is why we need the actual source evidence before saying the department is blank.

After identifying the real input, check how this integration handles it. Do not assume an empty string, null and an omitted field all cause the same update or clear the destination. Their representation and the operation's rules both matter.

Q39. Null or the word null?

Question: Support compares two JSON user-profile fields: "department": null and "department": "null". One has no quotes around null and one does. Are these the same input to a department conversion, and what should be inspected?

Read the teaching explanation

Explanation:

They are different. Unquoted null is JSON's marker for no value. Quoted "null" is text containing that word.

A conversion might treat the text as an unrecognized department rather than as the same condition as JSON null. The actual behavior depends on its supported configuration.

Identify the representation first, then inspect the handling rule and result. Similar-looking text does not make the two values interchangeable.

Q40. Most people are in Sales

Question: Projects requires a department code: SAL means Sales, FIN means Finance, and IT means IT. Daniel’s incoming department is missing. The company requires review for missing or unrecognized input. Should support default to SAL because most employees work in Sales?

Read the teaching explanation

Explanation:

That would turn missing information into a claim that Daniel belongs to Sales. The supplied policy requires review instead of a guess.

Obtain the legitimate source value and agreed handling process. Population frequency cannot determine one person's department.

A guessed code might satisfy a required-field constraint while misrepresenting the employee. Resolve the unknown through the appropriate owner rather than make the record look complete at the expense of accuracy.

Q41. No automatic fallback

Question: Okta prepares application values from a source department field. For one user the input is missing, but no source-substitution setting or target update behavior is supplied. Does that alone prove another source will be selected or an existing destination value will be cleared?

Read the teaching explanation

Explanation:

Neither outcome follows from the missing input alone. Source selection and target handling depend on the actual configuration and operation.

Inspect what the source contains, how the conversion treats that condition, and what any update sends and returns. An existing target value also needs its own read.

Keep the input observation separate from assumed consequences. Missing data identifies a question; it does not silently define a fallback or clearing action.

Q42. An unrecognized department

Question: An employee’s approved department is Legal. Projects currently accepts SAL for Sales, FIN for Finance, and IT for IT, with no Legal conversion defined. Company policy requires review of unrecognized input. What decision is needed before providing a target code?

Read the teaching explanation

Explanation:

Legal has no supplied representation in this table. Confirm the legitimate input and obtain an agreed destination representation or handling process through the responsible owners.

Do not invent a Sales or Finance code. If the application requirement needs another accepted department, that change must be defined rather than guessed in the mapping.

The uncovered input is the demonstrated issue. It is not evidence that Legal means one of the existing codes.

Ownership and mapping

Q43. How versus who

Question: Workday controls Daniel’s approved HR department. A mapping represents that value in Okta, and another prepares Projects’ required department code. How does the decision about ownership differ from the rule about representation?

Read the teaching explanation

Explanation:

Ownership identifies which system is allowed to control the business value. A mapping defines where information goes and how it is represented.

Here Workday owns the department, while the mappings prepare its appropriate forms in Okta and for Projects. Those responsibilities are connected but answer different questions.

A valid conversion does not authorize changing correct HR data to hide a downstream error. First preserve the business fact, then investigate its representation and delivery.

When the mapping applies

Q44. A correct expression and an old app profile

Read the teaching explanation

Explanation:

Inspect when the mapping applies and how existing prepared values are intended to receive the correction. A correct formula does not prove this existing record was recalculated.

Compare the supported behavior with the requirement, review other affected users, and plan the appropriate update process. Then verify both the app user profile and target account separately.

This discrepancy is already in the stored prepared value. A target-delivery check alone would not establish that the input to delivery was corrected.

Q45. Recalculate versus transmit

Question: An Okta mapping calculates an app user field only at creation. A later profile update may send the full stored app user profile, including that field. Does creation-only guarantee the field is absent from every later request, and is transmitting it the same as recalculating it?

Read the teaching explanation

Explanation:

No. Creation-only describes when the mapping calculates the value. It does not promise that a later request will leave the stored field out.

Imagine the field was calculated earlier and still holds SAL. Under the full-profile update behavior supplied here, that stored SAL can be sent again without the mapping working out a fresh department code. Sending the old answer and recalculating the answer are different actions.

Check the stored app user value and the actual outgoing request. That lets you explain both what Okta had prepared and what it sent, instead of using a timing label to guess the request's contents.

Q46. Compare three independent mapping situations

Question: For all three independent cases, Finance should become FIN in an app user profile held in Okta and then in the linked Projects account. A: the rule always produces SAL. B: preview and app user profile are FIN, target is SAL, and no update result is supplied. C: the expression is correct but creation-only, and an existing app user profile still holds SAL. Match each case to its next investigation.

Read the teaching explanation

Explanation:

For A, address the demonstrated wrong conversion against the approved FIN requirement. For B, inspect the delivery operation and target result because preparation is already correct. For C, inspect mapping timing and how existing prepared values should be recalculated.

Similar target symptoms can arise at different boundaries. Use the intermediate evidence to distinguish them.

One expression rewrite would not answer all three questions. Keep each case's current facts and missing result separate.
